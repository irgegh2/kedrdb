# KedrDB — собственная СУБД на Rust

Строим самостоятельную серверную SQL-СУБД. Название KedrDB (КедрDB), Rust и лицензия Apache 2.0 выбраны пользователем. Первая задача — магазин или сервис учета; долгосрочная цель — большая универсальная база данных.

Этапы 1–2 пройдены. Этап 3 проходит приемку: реализованы WAL, приватные изменения, storage commit/rollback, recovery и ротация журнала. Есть собственные страницы, ограниченный кэш, B+ tree и CLI проверки целостности. SQL-таблицы, конкурентные сессии и сетевой сервер впереди. Номер пакетов `0.1.0` — версия разработки, не выпуск 1.0.

## Запуск основы

Требуется Rust/rustup. Toolchain 1.94.1 закреплен в rust-toolchain.toml; внешних Cargo-зависимостей пока нет. Основа проверена локально на macOS ARM64 и в GitHub Actions на Ubuntu 24.04/x86_64 и macOS ARM64: [успешный запуск](https://github.com/irgegh2/kedrdb/actions/runs/37877080961).

Открытый репозиторий: [irgegh2/kedrdb](https://github.com/irgegh2/kedrdb). [GitHub Actions](https://github.com/irgegh2/kedrdb/actions) использует стандартные бесплатные для публичного репозитория Ubuntu/macOS runners. CI проверяет корректность и сборку; длительность его jobs не является benchmark скорости KedrDB.

```sh
cargo run -p kedr --offline -- doctor
cargo run -p kedr --offline -- storage-check .
cargo test --workspace --locked --offline
```

`storage-check` создает только собственный новый временный файл в указанном существующем каталоге, пишет, синхронизирует, открывает заново, проверяет байты и удаляет этот файл. При штатном выполнении существующие файлы сохраняются. Это проверка I/O, а не проверка SQL или транзакций. При аварийном завершении проверки ее временный файл может остаться.

Development store работает с ключами BIGINT и байтовыми значениями; это еще не SQL-таблицы. После сборки, в отдельном каталоге, пример:

```sh
kedr create-db demo
kedr put demo 42 'Кедр'
kedr get demo 42
kedr integrity-check demo
```

`create-db` создает новый каталог с WAL и удерживает OS lock. `kedr checkpoint demo` сохраняет основной файл и переключает журнал. Гарантии и консервативная остановка при corrupt tail описаны в [DURABILITY.md](docs/DURABILITY.md). Legacy `create-store` создает отдельный файл без WAL.

## Рабочая гипотеза первой версии

Серверная SQL-база на одном узле для небольших приложений: таблицы, индексы, транзакции, постоянное хранение, подключение приложений через ограниченный PostgreSQL wire protocol, резервное копирование и восстановление. Гипотеза о преимуществе — более простая установка и меньшие затраты ресурсов на узком наборе запросов. Преимущество в скорости предстоит измерить.

Полной совместимости с PostgreSQL и pgAdmin в версии 1.0 не обещаем. Поддержка конкретных драйверов и клиентов подтверждается интеграционными тестами и описывается в матрице совместимости.

## Что уже сделано

- Проверена доступность Rust: локально установлены `rustc 1.94.1` и `cargo 1.94.1`.
- Подготовлены план и критерии выпуска, продуктовый профиль и SQL-матрица.
- Пользователь подтвердил первую задачу: магазин/сервис учета, 95% чтения / 5% записи. Долгосрочная цель — большая универсальная СУБД.
- Выбраны название KedrDB (КедрDB) и лицензия Apache 2.0.
- Созданы три Rust crates: ядро, testkit и диагностическая CLI. Работают codecs, B+ tree, page store, WAL и storage transactions; SQL впереди.
- Есть проверки частичного I/O, ошибок sync, воспроизводимых операций и падения процесса; CI описывает Linux/macOS.
- Выполнены предварительные PostgreSQL-измерения в отдельном временном кластере; результаты сохранены вместе с проектом.
- Ранний незавершенный Python-набросок, созданный в этом чате, удален: продукт планируется на Rust.

## Следующий шаг

Технические материалы этапа 0 подготовлены. Название и лицензия выбраны; реальные пилоты, подтверждение спроса и проверка имени еще впереди. Весь этап 0 пока не отмечен завершенным. Реализация продолжается параллельно рыночной проверке.

После приемки WAL/recovery (этап 3) сразу реализуем конкурентные транзакции (этап 4). Надежность всей СУБД, совместимость SQL и лидерство по скорости пока не подтверждены.

Оценки в плане предполагают одного разработчика с ИИ и регулярную работу. Это предварительные ориентиры, не обещание даты выпуска.
