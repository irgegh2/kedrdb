# Бенчмарки и путь к лидерству по скорости

Статус: первый локальный сравнительный baseline завершен; [результаты и ограничения этапа 8](milestones/08.md). Приемка полного протокола и рыночный рейтинг еще не выполнены.

Пожелание пользователя: в конце разработки сравнить базу с разными СУБД и продолжать улучшение до лидерства по скорости. Финальный сравнительный отчет обязателен перед выпуском. Внутренние измерения начинаются раньше, чтобы архитектурные ошибки обнаруживались до финала.

## 1. Что означает «топ-1»

Лидерство требует определения: класс нагрузки, размер данных, оборудование, конкуренты, версии, настройки, транзакционные гарантии и метрика. Изменение любого пункта может изменить победителя.

Рабочая категория — серверная SQL-СУБД на одном узле для небольших приложений. Первичный показатель выбираем на этапе 0, например максимальное устойчивое число успешно завершенных транзакций в секунду при заданной p99 задержке. Порог задержки задается потребностью пользователя до сравнительного теста.

Успех: первое место среди заранее выбранных и проверенных конкурентов на заранее выбранной основной нагрузке, при правильных результатах и одинаковом контракте сохранности. Это еще не доказывает первое место среди всех существующих СУБД.

Если используем общий рейтинг по набору нагрузок, заранее публикуем формулу и веса. Геометрическое среднее нормированных результатов возможно, но не означает победу в каждой отдельной задаче. В отчете остаются результаты всех задач, в том числе проигрыши.

Предварительное конкурентное условие для 1.0 после уточнения этапа 0: доказанное лидерство по выбранной метрике скорости в выбранной категории. Победа только по размеру бинарного файла или памяти не подменяет эту цель пользователя. Если лидерство не достигнуто, продолжаем исследование/пересматриваем архитектуру, а срок 1.0 пересчитываем.

Достижимость лидерства не гарантируется. Даже после многих оптимизаций возможен предел диска/памяти/CPU или преимущество другой архитектуры. Выбор более узкой задачи допустим, но оформляется как новое условие соревнования, а не скрытая смена теста после проигрыша.

## 2. Готовые инструменты уже существуют

| Инструмент / набор | Для чего | Как применяем |
|---|---|---|
| [pgbench](https://www.postgresql.org/docs/current/pgbench.html) | Транзакционные сценарии, конкурентные клиенты, собственные скрипты | Первый PostgreSQL baseline и затем наш сервер после проверки протокола |
| [sysbench](https://github.com/akopytov/sysbench) | SQL-нагрузки OLTP, настраиваемые Lua-сценарии, throughput и latency | Сравнение с PostgreSQL/MySQL после проверки нужного SQL |
| [BenchBase](https://github.com/cmu-db/benchbase) | Нагрузки для разных SQL-СУБД через JDBC, например SmallBank, TPC-C, YCSB | Независимый набор сценариев при совместимости JDBC и SQL |
| [TPC-C](https://tpc.org/tpc-bm-categories/oltp5.asp) | Транзакционная обработка бизнес-операций | Дальнейшая проверка OLTP, когда хватает возможностей SQL |
| [TPC-H](https://tpc.org/tpch/) | Аналитические запросы и поддержка принятия решений | Отдельный будущий аналитический трек |
| [TPC-DS](https://www.tpc.org/tpc-bm-categories/decision-support5.asp) | Более широкий аналитический набор | Поздний этап расширения SQL и аналитической архитектуры |
| [YCSB](https://github.com/brianfrankcooper/YCSB/wiki/Core-Workloads) | Смеси чтения, обновления, вставки и сканирования записей | Проверка соответствующего record/key-value профиля с явным контрактом операций |

Инструмент и стандарт — разные вещи. Прогон сценария BenchBase, похожего на TPC-C, не является автоматически официальным результатом TPC. Измененный или частичный набор всегда называется измененным/частичным, с перечнем отличий.

Стандартный pgbench и sysbench могут использовать SQL, которого нет в нашей первой версии. До поддержки запускаем явно названные собственные скрипты; не объявляем недоступный сценарий пройденным. TPC-H/DS не входят в обязательный состав узкой транзакционной 1.0.

## 3. Конкуренты и режимы

Первоначальные кандидаты: PostgreSQL, MySQL, MariaDB и наш сервер. На этапе 0 определяем, какие системы действительно используются целевым клиентом, и фиксируем актуальные версии на дату испытания.

SQLite можно проверить в отдельном встраиваемом треке. Сравнение прямого вызова в одном процессе с сетевой SQL-базой отвечает другой задаче, чем сравнение четырех серверов. Эти результаты не объединяем в один рейтинг без явного общего контракта приложения.

Аналитические СУБД, например DuckDB и ClickHouse, добавляем, если вводим аналитический класс. Распределенные базы сравниваем отдельно при равных требованиях репликации/доступности. Отсутствие этих гарантий в нашем движке не является доказательством превосходства в распределенной категории.

Для каждой системы допускаем ее нормальный документированный способ настройки, индексы и подходящий план запроса. Фиксируем одинаковые ресурсы и гарантии, а не искусственно одинаковое название каждого параметра. На настройку конкурентов выделяется сопоставимое время; по возможности конфигурацию проверяет знающий эту систему человек.

## 4. Наш начальный открытый набор

Создаем собственные сценарии независимо от наличия готовых: они покрывают продукт, наш поддерживаемый SQL и проверку правильности.

| ID | Сценарий | Что проверяем |
|---|---|---|
| W01 | SELECT по первичному ключу: существующий и отсутствующий | Индексное чтение и latency |
| W02 | SELECT по вторичному индексу с разной избирательностью | Индекс, выбор плана, реальная стоимость получения строк |
| W03 | Диапазон с ORDER BY и LIMIT | Диапазонный доступ и ранняя остановка |
| W04 | Одиночный INSERT с устойчивым COMMIT | Реальную стоимость надежной записи |
| W05 | INSERT пакетами 10/100/1000 в транзакции | Амортизацию commit без подмены одиночного режима |
| W06 | UPDATE/DELETE по ключу с вторичным индексом | Согласованность и стоимость поддержки индекса |
| W07 | Смесь 95% чтения / 5% записи и отдельно 50% / 50% | Конкурентность и предел блокировок |
| W08 | Прикладная транзакция заказа: проверка товара, изменение остатка, запись заказа | Корректность и throughput нескольких операций |
| W09 | Простой INNER JOIN и COUNT(*) | Прикладные чтения, зафиксированная семантика |
| W10 | Долгий читатель вместе с писателем, checkpoint под нагрузкой | Хвосты latency и предсказуемость |
| W11 | Рост/удаление/повторная вставка | Разрастание файлов, переиспользование страниц, стабильность |
| W12 | Restart/recovery и backup/restore после нагрузки | Рабочие характеристики эксплуатации |

Точная смесь W08 зависит от поддерживаемых выражений SQL. Если арифметического UPDATE нет, используется чтение и параметризованное обновление в транзакции с эквивалентной изоляцией у всех участников.

Рабочая сетка измерений:

- Логический объем 100 МБ, 1 ГБ и 10 ГБ; дополнительно объем больше доступного кэша минимум в четыре раза.
- Строки примерно 128 байт, 1 КиБ и близко к максимальному поддерживаемому размеру.
- Клиенты 1, 8 и 32; далее до измеренного насыщения.
- Равномерный доступ, горячие ключи и неоднородное распределение по фиксированным seed.
- Теплый кэш и отдельные холодные испытания с документированным способом сброса кэшей. Перезапуск сервера сам по себе не очищает кэш ОС.
- Весь timed путь включает получение и проверяемое потребление результата клиентом; не только возврат указателя на внутренний буфер.

Не весь декартов набор обязан выполняться ежедневно. Этап 0 фиксирует основной suite для рейтинга; расширенная сетка проверяет границы и не должна скрываться из итогового отчета.

## 5. Правила честного сравнения

1. Одна и та же аппаратная среда, CPU/RAM budget, накопитель, ОС и политика питания. Серверы испытываются по очереди; порядок прогонов перемешивается.
2. Одинаковый логический набор данных, поддерживаемые типы, значения, индексы и результат запросов. Отличия физического представления фиксируются.
3. Одинаковое подтверждение надежной записи. Для PostgreSQL не отключаем fsync или synchronous_commit ради «похожих настроек». Для других систем проверяем эквивалентный контракт commit.
4. Одинаковая заявленная изоляция. Если наш сервер сериализует транзакции, сравнение в слабой изоляции у конкурента помечается как отдельный режим.
5. Сопоставимый путь клиента: сеть/локальный сокет, prepared statements, connection reuse и размер результата. Запросы с открытием нового соединения — отдельный сценарий.
6. Подготовка, загрузка и прогрев отделены от измерения. Цена загрузки и построения индексов измеряется отдельно.
7. Лимит времени ответа и ошибки включаются в результат. Быстрый отказ не считается успешно выполненным запросом.
8. Генератор нагрузки не является узким местом. Измеряем его CPU и достижимый offered rate; при необходимости переносим его на отдельную одинаково используемую машину.
9. И throughput, и задержки сохраняются. Closed-loop тест с фиксированными клиентами дополняем open-loop под заданной интенсивностью, чтобы очередь и перегрузка не исчезали из latency.
10. Обслуживание включено: checkpoint, fsync, очистка/переиспользование, рост WAL. Короткий прогон до первой фоновой работы не доказывает устойчивую скорость.
11. Конфигурации конкурентов разумно настроены и опубликованы. Преднамеренно неудачный индекс/план конкурента не является преимуществом.
12. Выполняется независимая проверка данных. Неверный результат дисквалифицирует прогон независимо от скорости.

## 6. Методика прогонов и отчет

Для разведочных локальных измерений допустимы короткие прогоны с пометкой «не итоговые».

Финальный сравнительный режим:

- Сохранить workload specification до финальной настройки. Тесты реального пилота, которые не использовались для ежедневного тюнинга, оставить отдельным контрольным набором.
- Прогревать до стабильного режима; предварительный ориентир — минимум 5 минут, дольше при необходимости checkpoint/cache stabilization.
- Измерять каждую обязательную комбинацию минимум 30 минут, не менее пяти независимых прогонов. Продлить прогон, если фоновое обслуживание еще не наблюдалось.
- Между независимыми прогонами восстановить согласованное исходное состояние и задокументировать cache mode.
- Сохранить raw samples/гистограммы, throughput, p50/p95/p99, ошибки, таймауты, CPU, RSS, IO, WAL и размер базы.
- Для основной метрики дать оценку разброса и 95% доверительный интервал по независимым прогонам. Не выдавать миллионы зависимых запросов одного прогона за миллионы независимых экспериментов.
- Проверить устойчивость преимущества на другой конфигурации машины или получить независимое воспроизведение перед широким заявлением лидерства.
- Когда интервалы и шум не позволяют отличить участников, результат — статистически неразличимый, а не доказанное первое место.
- Итоговое сравнение выполнить на release candidate после пилотного периода. Любое последующее изменение критичного кода требует повторной проверки затронутых сценариев.

Состав будущего BENCHMARK_REPORT.md:

| Поле | Что сохраняем |
|---|---|
| Идентичность | Дата, commit нашего сервера, версии конкурентов, harness commit |
| Среда | CPU, RAM, SSD, ОС, файловая система, limits, сеть, питание |
| Контракт | Durability, isolation, индексы, типы, число клиентов |
| Данные | Генератор, seed, объем, распределение, checksums |
| Настройки | Полные конфиги и команды запуска каждого участника |
| Результат | Все прогоны, ошибки, throughput, latency, ресурсы |
| Проверки | Корректность, recovery, финальное состояние данных |
| Вывод | В чем выиграли, в чем проиграли, границы утверждения |

## 7. Цикл улучшения до лидерства

1. Выполнить заранее выбранную нагрузку, проверить данные и сравнить результаты.
2. Найти узкое место профилем CPU, IO, ожиданий и аллокаций.
3. Записать гипотезу и ожидаемый эффект одного изменения.
4. Реализовать изменение, выполнить связанные тесты корректности/сбоев.
5. Повторить измерения и сравнить с исходным результатом на нескольких прогонах.
6. Оставить подтвержденное улучшение; отклонить ухудшение или неподтвержденную сложность.
7. Если предел архитектурный, создать новое решение и пересчитать этапы, например добавить MVCC, group commit или другой layout.
8. Повторять цикл; после достижения лидерства проверить контрольный набор и независимое воспроизведение.

Group commit требует нескольких готовых писателей или измененной схемы очереди. Его нельзя просто прикрутить к эксклюзивной блокировке, которая допускает только одного ожидающего commit писателя. Такая оптимизация меняет архитектурные допущения и тесты.

Расширение цели «все нагрузки, все СУБД, любое оборудование» не имеет конечного проверяемого условия. Полезная амбициозная цель — стать лучшим в выбранной категории и затем последовательно расширять область подтвержденного лидерства.
