# KedrDB и Kedr Studio: описание проекта для преподавателя

Состояние на **10 октября 2026 года**. Документ описывает работающие части и отдельно план первой версии. **SQL-версия 1.0 пока не выпущена.**

## Краткое предложение

Я разрабатываю собственную СУБД **KedrDB** на языке **Rust**, с помощью искусственного интеллекта. Проект включает собственное хранение данных, индекс B+ tree, журнал изменений и восстановление после сбоя. Это самостоятельный движок: PostgreSQL или SQLite не встроены внутрь под новым названием.

Я хотел бы использовать KedrDB для тех лабораторных работ, требования которых она сможет выполнить, и дополнительно показать устройство СУБД на уровне исходного кода и тестов. Начальный SQL уже реализован локально: можно создавать таблицы и выполнять простые запросы через CLI. Этап 5 принят на Linux/macOS после сверки с PostgreSQL. Для согласования лабораторных нужно продемонстрировать именно требуемые преподавателем команды.

Реализовано отдельное приложение **Kedr Studio**, также на Rust; проверены на macOS/Linux: подключение к серверу, список таблиц, редактор SQL и результаты запросов. Прошу рассматривать замену стандартной СУБД для конкретных лабораторных после демонстрации нужных команд и проверки результатов. Если задание требует возможностей, которых еще нет, его можно выполнить в PostgreSQL и сравнить результаты с поддерживаемой частью KedrDB.

## 1. Что это за база данных

KedrDB — проект серверной реляционной SQL-СУБД для одного компьютера или сервера. Первая область применения — небольшое приложение учета или магазина: пользователи, товары, заказы и изменения остатков. Долгосрочная цель — развивать полноценный продукт; первая версия ограничивает состав функций до проверяемого минимума.

Сервер хранит данные и выполняет SQL. Kedr Studio является графическим клиентом, который отправляет команды серверу и показывает ответ. Хранение, ограничения и транзакции проверяет сервер; приложение не редактирует файлы базы напрямую.

Проект открыт на GitHub: [irgegh2/kedrdb](https://github.com/irgegh2/kedrdb). Лицензия — Apache-2.0. Внутренний номер Rust-пакетов `0.1.0` сейчас обозначает разработку, а не готовый выпуск 1.0.

## 2. Как проект создается и что используется

Разработка ведется итерациями: требования → архитектурное решение → код → проверка с эталоном и управляемыми ошибками → сохраненный отчет. Искусственный интеллект используется существенно: помогает проектировать архитектуру, писать и разбирать Rust-код, готовить тесты и документацию. Проект не представляется как полностью написанный вручную без помощи ИИ. При защите я должен уметь объяснить решения, воспроизвести проверки и показать ограничения.

| Инструмент | Для чего используется |
|---|---|
| Rust, закрепленный toolchain 1.94.1 | Ядро, тестовые инструменты, CLI, сервер и GUI |
| Cargo workspace | Сборка нескольких частей проекта и запуск тестов |
| rustfmt / Clippy | Форматирование и статические проверки Rust-кода |
| Git / GitHub | История ревизий, открытые исходники и отчеты |
| GitHub Actions | Автоматические проверки на Ubuntu и macOS |
| Собственный testkit | Ошибки чтения/записи/sync, частичная запись, случайные сценарии и crash simulation |
| PostgreSQL / pgbench | Эталон поддерживаемого SQL и будущие сравнительные измерения; PostgreSQL не хранит данные KedrDB |
| Python | Вспомогательные скрипты проверки и подготовки отчетов; не движок базы |

На подтвержденной ревизии этапа 3 ядро, testkit и CLI используют стандартную библиотеку Rust без сторонних Cargo-зависимостей. С этапа 5 используется sqlparser 0.63.0 для tokenizer и его зависимость log; grammar, catalog и executor собственные. Для GUI используется eframe/egui 0.35.0; для сети Tokio 1.53.2; клиентский драйвер tokio-postgres 0.7.18; TLS — rustls 0.23.45/ring; SCRAM — rsasl 2.3.1. Выбор фиксируется в отчете и [списке компонентов](../THIRD_PARTY.md); собственная криптография не разрабатывается.

Локальная SQL-демонстрация:

```sh
cargo fetch --locked
cargo build -p kedr --release --locked --offline
target/release/kedr create-db sql-lab-demo
target/release/kedr sql sql-lab-demo 'CREATE TABLE students (id BIGINT PRIMARY KEY, name TEXT NOT NULL)'
target/release/kedr sql sql-lab-demo "INSERT INTO students (id,name) VALUES (1, 'Анна')"
target/release/kedr sql sql-lab-demo 'SELECT id,name FROM students ORDER BY id'
```

`sql-lab-demo` — новый отдельный каталог. Ответ CLI выводится как JSON. Доступна также прежняя демонстрация ключей и значений в другом каталоге:

```sh
cargo run -p kedr --offline -- create-db lab-demo
cargo run -p kedr --offline -- put lab-demo 1 'Первая запись'
cargo run -p kedr --offline -- get lab-demo 1
cargo run -p kedr --offline -- integrity-check lab-demo
```

`lab-demo` должен быть новым путем. Это демонстрация хранения, **не SQL-таблица**.

### Как проходит запрос

```text
Kedr Studio / psql / драйвер приложения
              ↓ SQL и отдельные параметры, TCP + TLS
kedr-server: проверка пакета → SQL-сессия (SCRAM при подключении)
              ↓
Parser: разбирает SQL → Binder: проверяет имена и типы
              ↓
Executor: выбирает индекс или сканирование и выполняет запрос
              ↓
Транзакция: приватные страницы → WAL → fsync → commit
              ↓
Постоянные файлы KedrDB → результат или SQLSTATE клиенту
```

Это отдельные процессы: закрытие Studio не удаляет базу и не останавливает сервер. Для новой базы CLI один раз создает каталог, затем сервер открывает его и держит файловую блокировку. Несколько клиентов работают через сервер; второй сервер тот же каталог открыть не может. PostgreSQL нужен для сравнения правильности, а не для выполнения наших запросов. [Пошаговое подключение](CONNECTIONS.md).

## 4. Что войдет в KedrDB 1.0

Первая 1.0 задумана как узкий MVP: минимальный полезный продукт для выбранной задачи с проверенными данными и транзакциями. Состав ниже — **цель разработки, а не список уже работающих функций**.

- Таблицы: `CREATE TABLE`, `DROP TABLE`, простое `ALTER TABLE ADD COLUMN` для nullable столбца без DEFAULT; сохранение схемы между перезапусками.
- Типы: `INT`, `BIGINT`, `TEXT`, `BOOLEAN`, `NULL`. Первичный ключ каждой таблицы — один явно заданный `BIGINT`.
- Ограничения: `PRIMARY KEY`, `NOT NULL`, `UNIQUE`, простой одноколоночный `FOREIGN KEY` с немедленной проверкой и `NO ACTION`.
- Данные: `INSERT`, `SELECT`, `UPDATE`, `DELETE`, параметры запросов, `WHERE` со сравнениями и `AND`, `IS NULL`, сортировка и `LIMIT`.
- Запросы между таблицами: простой `INNER JOIN` по равенству; из агрегатов — `COUNT(*)`.
- Индексы: первичный B+ tree и одноколоночные вторичные индексы; `EXPLAIN` для отображения выбранного доступа.
- Транзакции: autocommit, `BEGIN`, `COMMIT`, `ROLLBACK`, `READ ONLY`, изоляция на основе глобальной блокировки, отмена и лимиты времени/памяти.
- Подключение: сервер, аутентификация, TLS для удаленного доступа, проверенное подмножество PostgreSQL wire protocol, psql и выбранный драйвер.
- Эксплуатация: журнал, восстановление, проверенные backup/restore, SQL export/import, логи и инструкции установки.

Backup может потребовать остановки записи. Одновременно пишет одна транзакция; запись блокирует читателей, долгие читатели задерживают писателя. Целевой проверяемый объем — 1–10 ГБ на одном узле; это будущий диапазон испытаний, не измеренный сегодня предел.

Не входят в первый состав: полный SQL PostgreSQL, MVCC, параллельные писатели, JSONB/NUMERIC/TIMESTAMP/UUID, полный набор агрегатов, подзапросы/CTE/оконные функции, хранимые процедуры, расширения, репликация, кластер и автоматическое переключение на резервный сервер. Крупные значения сверх начального лимита строки также требуют дальнейшей разработки.

## 5. Что войдет в Kedr Studio 1.0

Это минимальное desktop-приложение на Rust, первоначально для macOS и Linux. Простая компоновка: слева подключения и таблицы, справа редактор SQL, снизу результаты и сообщения. Нужны читаемый текст, понятные кнопки, корректные состояния загрузки и ошибки; сложный визуальный дизайн будет развиваться позже.

В MVP входят подключение/отключение, список таблиц и столбцов, редактор и выполнение SQL, таблица ограниченного результата с корректным NULL, копирование значения, сообщения об ошибке, статус соединения/транзакции, отмена запроса и сохранение/открытие `.sql` файла. Схема и данные создаются/меняются SQL-командами. Пароль вводится при подключении; его постоянное сохранение не требуется для MVP.

Не требуются к 1.0 визуальный конструктор таблиц, ER-диаграммы, редактор строк с массовой записью, AI-помощник, сложные dashboards, мастера переноса/backup и полноценный аналог всех возможностей pgAdmin. Backup, restore и перенос остаются возможностями СУБД/CLI; графические мастера могут появиться позже. В основе привычного рабочего окна ориентируемся на [Query Tool pgAdmin](https://www.pgadmin.org/docs/pgadmin4/latest/query_tool.html), без обещания полного функционального равенства.

Django ORM, миграции и Django Admin пока не поддерживаются: работа Python-драйвера psycopg не означает работу всего фреймворка. Поддержка Django потребует отдельного адаптера и расширения/проверок SQL; первая прикладная поддержка запланирована как цель версии 2.0 после MVP. [Подробности](CONNECTIONS.md#django).

## 6. Насколько 1.0 приблизится к PostgreSQL

Для узкого сценария «создать несколько таблиц, записать данные, сделать простые выборки/соединение, проверить ограничения и транзакцию» планируется похожий рабочий процесс. По полноте функций, параллельной нагрузке, экосистеме и зрелости 1.0 будет существенно уступать PostgreSQL. Процент вроде «80% PostgreSQL» здесь ничего достоверно не измеряет.

| Область | План KedrDB 1.0 относительно PostgreSQL |
|---|---|
| Базовые таблицы, CRUD, ограничения | Поддерживаемое подмножество, достаточное для части прикладных и учебных задач |
| Сложные запросы и типы | Значительно меньше возможностей |
| Транзакции | Проверяемая простая модель; меньше конкурентности |
| Совместимость | Часть SQL/protocol, только проверенные клиенты; не автоматическая замена любого приложения PostgreSQL |
| Надежность | Собственные проверки и обязательные испытания; сопоставимая зрелость пока не установлена |
| Скорость | Сравнение впереди; преимущество и первое место пока не подтверждены |
| GUI | Основной сценарий SQL editor/results; значительно меньше функций, чем у pgAdmin |

У PostgreSQL модель MVCC позволяет обычному чтению и записи не блокировать друг друга; наша начальная глобальная блокировка этого преимущества не имеет. [Документация PostgreSQL](https://www.postgresql.org/docs/current/mvcc-intro.html). Состав его учебного SQL шире нашего первого набора, а расширения являются отдельной полноценной возможностью. [SQL tutorial](https://www.postgresql.org/docs/current/tutorial-sql.html), [CREATE EXTENSION](https://www.postgresql.org/docs/current/sql-createextension.html).

## 7. Какие лабораторные можно предложить

После готовности SQL-этапа и проверки нужных команд разумные кандидаты: создание таблиц с базовыми типами; CRUD; первичные/уникальные/внешние ключи; простые фильтры, сортировка и соединение; commit/rollback; сравнение индексного и полного поиска; изучение страниц, B+ tree, WAL и восстановления по исходникам.

Не подходят без дополнительной реализации задания, требующие, например, `GROUP BY`/`SUM`/`AVG`, подзапросов, представлений, триггеров, процедур, отдельных ролей и `GRANT`, специфических типов PostgreSQL или его расширений. Отсутствие этих возможностей нельзя компенсировать сменой названия команды.

Предлагаемый порядок: получить перечень обязательных операций лабораторной → сопоставить с фактически поддерживаемыми возможностями конкретной версии → продемонстрировать выполнение и правильный результат → согласовать использование KedrDB. Для защиты можно предоставить исходники, схему хранения, архитектурные решения, тесты и сравнение тех же запросов с PostgreSQL.

Пример поддерживаемого учебного сценария (в редакторе выполнять по одному оператору или выделять один оператор):

```sql
CREATE TABLE students (
    id BIGINT PRIMARY KEY,
    name TEXT NOT NULL,
    study_year INT
);
INSERT INTO students (id, name, study_year) VALUES (1, 'Анна', 2);
SELECT id, name FROM students WHERE study_year >= 2 ORDER BY id LIMIT 10;
BEGIN;
UPDATE students SET study_year = 3 WHERE id = 1;
ROLLBACK;
```

## 8. Что будет следующим

Этап 5 — начальный SQL — принят. Техническая реализация этапа 6 — минимальный Kedr Studio, сетевой сервер и настоящая интеграция — проходит окончательные проверки. Этапы 7–10 добавляют обслуживание, измерения, исправления по пилотам и поставку. Расширение GUI и сложных возможностей базы остается дальнейшим развитием.

Для учебной демонстрации можно использовать подходящую проверенную alpha-версию до рыночного выпуска 1.0. **Минимальный функционал не означает минимальные требования к сохранности:** рыночная 1.0 все равно требует обязательных тестов, восстановления, документации и полевых проверок. Начальный локальный SQL проверен; дата готовности полного выпуска пока не гарантирована.
