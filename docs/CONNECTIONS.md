# Подключение к KedrDB

Рабочая реализация этапа 6, 10 октября 2026. Приемка macOS/Linux пройдена; [отчет и проверенные версии](milestones/06.md). KedrDB реализует ограниченную часть протокола PostgreSQL; это собственная СУБД и собственный SQL-каталог.

## Запуск

```sh
cargo build --workspace --locked
mkdir -p data
# Новый каталог базы; существующий не перезаписывается.
target/debug/kedr create-db data/shop
# В терминале пароль вводится скрыто; в автоматизации допускается ограниченный stdin.
target/debug/kedr-server init-auth data/shop-auth admin
target/debug/kedr-server serve --data data/shop --auth data/shop-auth
# В другом терминале:
target/debug/kedr-studio
```

В Studio: адрес `127.0.0.1`, порт `55432`, база `kedrdb`, пользователь `admin`, заданный пароль. Числовой loopback разрешен без TLS для локальной работы. Для сетевого адреса Studio требует TLS и файл CA. TLS проверяет цепочку и имя узла; отключения проверки сертификата нет. Пароль не сохраняется в профиле, файле SQL или журнале. При закрытии диалога/отправке подключения принадлежащая GUI строка очищается; драйвер получает пароль в памяти на время аутентификации. Это не гарантия удаления всех копий из памяти ОС/библиотек.

Пример SQL для редактора — выполнять каждый оператор отдельно либо выделять один оператор:

```sql
CREATE TABLE products (id BIGINT PRIMARY KEY, name TEXT NOT NULL, stock INT);
INSERT INTO products (id, name, stock) VALUES (1, 'Кедровый блокнот', 10);
SELECT * FROM products ORDER BY id;
BEGIN;
UPDATE products SET stock = stock - 1 WHERE id = 1;
ROLLBACK;
```

Одна команда протокола Query/Parse содержит один SQL-оператор. Скрипт из нескольких операторов одним вызовом отклоняется; `psql` интерактивно/через stdin отправляет операторы отдельно. Для параметров приложения используйте драйвер: `$1`/`$2` отдельно от значений. GUI выполняет введенный либо выделенный SQL, без панели параметров.

## TLS и учетная запись

```sh
target/debug/kedr-server serve --data data/shop --auth data/shop-auth \
  --listen 0.0.0.0:55432 --tls-cert server.crt --tls-key server.key
psql 'host=db.example.org port=55432 dbname=kedrdb user=admin sslmode=verify-full sslrootcert=ca.crt'
```

На нелокальном listener TLS обязателен, незашифрованный Startup отклоняется. Нужен сертификат с подходящим SAN, выпущенный доверенным CA; тестовый генератор служит только проверке. Приватный ключ и файл verifier должны быть недоступны группе/остальным (`0600`). TLS 1.2/1.3 реализованы rustls/ring, без собственного шифрования. Учетная запись в этой версии одна, административная, с полным доступом к выбранной базе. Роли/GRANT/мультиарендность еще не реализованы.

Аутентификация — SCRAM-SHA-256 через rsasl. В файле verifier: версия, пользователь, случайная соль, число итераций, StoredKey и ServerKey; нет открытого пароля или SaltedPassword. Принимается пустой SCRAM authid libpq только после проверки Startup.user и криптографического proof. Проверяется результат Validation, одного Finished недостаточно. SCRAM-SHA-256-PLUS/channel_binding=require пока не поддерживаются. Пароль не передается в argv и не выводится в логи; сервер журналирует только собственный запуск/системные отказы, без SQL/пакетов.

## Протокол и каталог

Протокол PostgreSQL v3.0: Startup, SSLRequest, отказ GSSENC, AuthenticationSASL/Continue/Final/OK, ParameterStatus, BackendKeyData, ReadyForQuery; Simple Query и Extended Parse/Bind/Describe/Execute/Close/Flush/Sync. Ошибка Extended включает пропуск сообщений до Sync. Execute с положительным max_rows сохраняет ограниченный результат и возвращает PortalSuspended. Параметры/результаты: OID 23 INT, 20 BIGINT, 25 TEXT, 16 BOOLEAN; входной OID 21 SMALLINT приводится к INT (нужен автоматическому выбору целого в psycopg); text и binary, NULL (`-1`). Остальные OID/сообщения — явная ошибка. Системные pg_catalog и расширения PostgreSQL не эмулируются.

`server_version=16.0-KedrDB-0.1.0` — числовой префикс для разбора выбранными драйверами, а не версия PostgreSQL или заявление о полной совместимости. Настоящие версия/контракт доступны через `SHOW KEDR STATUS`: `api_version`, `server_version`, `transaction_status` (I/T/E). API 1 согласуется Studio перед получением объектов; неизвестный контракт отклоняется. Статус доступен также в abort-состоянии для отображения необходимости ROLLBACK.

Каталог: `SHOW TABLES`, `SHOW COLUMNS FROM "table"`, `SHOW INDEXES FROM "table"`. Схема читается из того же транзакционного каталога, включая собственную незакоммиченную DDL. PRIMARY KEY отображается отдельно; SHOW INDEXES перечисляет вторичные индексы. Parse/Describe связывает имена и типы без выполнения записи и сканирования таблицы.

BEGIN/COMMIT/ROLLBACK — явные транзакции; ошибка требует ROLLBACK. COMMIT после abort сервер приводит к ROLLBACK. Extended-запросы вне явной транзакции объединяются до Sync: успех фиксируется, ошибка откатывает цикл. Подтверждение драйвера завершается после ReadyForQuery. Durability обеспечивает WAL ядра. Неопределенный COMMIT (SQLSTATE 40003) или потеря соединения никогда не повторяются автоматически.

## Лимиты и остановка

| Ресурс | Лимит |
|---|---|
| Входящий startup / auth payload | 8 КиБ |
| Входящий frame до выделения памяти | 256 КиБ |
| SQL / параметры | 64 КиБ / 256 значений |
| Сокеты до/после auth / SQL-сессии | 64 / 32 |
| Имена statement/portal, количество | 63 байта / по 16 |
| Параметры всех порталов | 1 МиБ |
| Сохраненные результаты порталов | 8 МиБ на соединение |
| Каталог | 128 таблиц, 256 столбцов в таблице |
| Startup + TLS + SCRAM | 8 секунд суммарно |
| Начатый frame / запись в сокет | 5 секунд |
| Ожидание нового frame | 300 секунд |
| Блокировка / transaction lifetime / idle in transaction | 5 / 300 / 60 секунд |
| Studio: подключение / операция / ответ после отмены | 8 / 30 / до 6 секунд |
| Studio: сохраняемые строки / данные результата | 1000 / 2 МиБ |

Оценочные лимиты данных результата и рабочей памяти ядра — по 8 МиБ; длинный результат GUI дренирует через драйвер, сохраняет ограниченную часть и явно сообщает об усечении. Большое чтение не заменяется молча другим SQL с LIMIT. Пределы данных результата/параметров не являются жесткой границей RSS процесса: структуры Rust/драйвера, аллокатор и TLS добавляют память. Измерения RSS и эксплуатационные бюджеты относятся к этапу 8. Входящие сообщения стоят в очереди из одного элемента. Отмена требует пары случайных pid/secret сессии; неправильный ключ игнорируется. EOF отменяет работающий запрос; незакоммиченная явная транзакция откатывается при уничтожении сессии. Между запросами idle-cancel не обещает отменить будущую работу.

Ctrl+C/SIGTERM прекращает прием, отменяет сессии и дожидается освобождения рабочих потоков/файловой блокировки. Ожидание системного fsync невозможно безопасно прервать средствами ядра; сетевые таймауты не гарантируют завершение зависшего ядра ОС за фиксированное время. WAL не удаляется. Второй сервер не может открыть тот же каталог; после штатного выхода каталог открывается вновь.

## Матрица клиента и воспроизведение

Окончательные версии и исходы проверок фиксируются в отчете этапа, без обещания работы любых драйверов. Целевой Rust-драйвер: tokio-postgres 0.7.18, TLS-адаптер tokio-postgres-rustls 0.14.0. psql проверяется отдельно с SCRAM и verify-full; psycopg 3 — дополнительная проверка, если установлен. pgAdmin/ORM/introspection PostgreSQL пока не заявлены совместимыми.

```sh
cargo test -p kedr-server -p kedr-studio --locked
cargo build --workspace --locked
cargo build -p kedr-studio --features screenshot --locked
python3 tools/check_stage6_clients.py --psql /path/to/psql --output artifacts/stage6/clients --studio
```

Скрипт создает временную базу, временный пароль/CA и отдельный случайный порт, затем завершает сервер; существующий PostgreSQL и базы пользователя не использует. Результат — summary.json и снимок настоящего окна. `--connect-test`/`--test-ca`, `--preview-results` и `KEDR_STUDIO_SCREENSHOT` служат диагностике; обычное окно запускается пустым и без демонстрационных надписей. Публичный репозиторий не содержит тестовых/пользовательских приватных ключей или паролей.

## Django

На 10 октября 2026 Django ORM, migrations и Django Admin с KedrDB не поддерживаются и не проверены. Проверка psycopg подтверждает выбранные SQL-вызовы драйвера, а не работу встроенного backend `django.db.backends.postgresql`. В исходниках Django 6.0 этот backend использует, например, DATE/TIMESTAMP/NUMERIC, identity для AutoField и LIKE; в текущем SQL KedrDB этих возможностей нет. Также нужна отдельная реализация introspection/schema editor и корректное поведение транзакций для выбранных операций ORM.

Django допускает сторонние database backends. Возможный путь — отдельный пакет `django-kedrdb`, который сообщает реальные capabilities, генерирует поддерживаемый SQL и использует наш каталог. Такой пакет пока не создан; имя условное. Сначала фиксируем версии Django/psycopg и поддерживаемые модели/операции, затем проверяем migrate, CRUD/QuerySet, ошибки/rollback, introspection и выбранный сценарий Django Admin. Обычный Django-проект должен пройти проверки целиком до заявления о его совместимости.

По подтвержденному пользователем плану, после завершения 1.0 начинается разработка и постоянная проверка Django на стенде. Первая прикладная поддержка Django — цель [версии 2.0](VERSIONS.md#20--обычному-приложению-хватает-ежедневных-возможностей): модели/CRUD, согласованные миграции, транзакции и тестовый проект с Django Admin. SQL/типы и SAVEPOINT, нужные этому сценарию, входят в тот же план. Это будущая функция, не уже выпущенная совместимость; поддержка любых Django-проектов не обещана. В 11.0 расширяется экосистема ORM. Состав MVP 1.0 остается прежним.

Источники: [сторонние backend Django](https://docs.djangoproject.com/en/6.0/ref/databases/#using-a-3rd-party-database-backend), [официальный PostgreSQL backend, ветка 6.0](https://github.com/django/django/blob/stable/6.0.x/django/db/backends/postgresql/base.py).
