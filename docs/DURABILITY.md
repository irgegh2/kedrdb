# Запись и восстановление: текущий контракт

Разработка, этап 3. Проверяемые правила открытых файлов описаны ниже; инженерная приемка и точные результаты — в [отчете](milestones/03.md). Это не сертификация накопителя при отключении питания и не выпуск 1.0.

## Успешный commit

Изменения дерева, свободных страниц и metadata сначала находятся только в приватном наборе полных страниц. Даже вытеснение грязной страницы из кэша пишет в этот набор. Лимит — 256 страниц по 16 КиБ, включая metadata; превышение откатывает транзакцию до записи WAL.

Порядок: PAGE_IMAGE записи → COMMIT → `sync_all` журнала → применение страниц и длины основного файла → `sync_all` основного файла → возврат успеха вызывающему коду. Отправка сетевого ответа будет отдельным действием сервера. Успешный commit должен сохраниться; отсутствие ответа не доказывает откат.

Ошибка append/sync журнала или применения уже подтвержденных страниц дает KD3002 (неопределенный исход). Дальнейшая запись через этот handle запрещена. Нужно закрыть его и выполнить recovery. `fsync` мог выполнить работу и затем сообщить ошибку: поэтому повтор всей бизнес-операции без идентификатора операции может создать дубликат.

Rollback и Drop незавершенной транзакции не пишут в основной файл и журнал. Текущее ядро имеет одного владельца; межсессионные блокировки относятся к этапу 4.

## Файлы и checkpoint

`create-db` создает новый каталог с правами 0700 и никогда не перезаписывает существующий путь. В каталоге находятся `.lock`, неизменяемая `.identity`, `data.kdr`, `wal/<16 hex digits>.wal`. OS lock принадлежит процессу весь срок открытой базы; блокировки advisory, они не защищают от программы, намеренно обходящей API. Существующие symlink members отклоняются.

Идентификатор базы защищен CRC32C отдельно от изменяемых metadata. Metadata version 2 содержит LSN последнего примененного commit и флаг WAL protection. Обычный B+ tree API не открывает такой файл для прямой записи в обход WAL. Legacy `create-store` создает version 1 без этих гарантий; его нельзя выдавать за транзакционную базу.

Новый каталог и имена файлов синхронизируются до первого успешного commit. Checkpoint: основной файл sync → exclusive создание следующего сегмента → header sync → sync каталога WAL → удаление старых сегментов → sync каталога WAL. Новый header содержит UUID, предыдущие transaction ID/commit LSN и следующий LSN. Переход выполняется только между транзакциями; default threshold 128 МиБ, фактический сегмент может превысить threshold на размер одной транзакции.

После любого отказа checkpoint handle недоступен до reopen. Старый журнал нельзя удалять раньше устойчивого основного файла и имени полного нового сегмента. После checkpoint для восстановления нужен основной файл и последний сегмент. Журнал не является резервной копией: потеря накопителя или файлов после удаления истории требует backup, который относится к этапу 7.

При open проверяются identity, имена и непрерывный сохраненный суффикс сегментов. Последний сегмент с header короче 128 bytes при наличии предшественника означает прерванное создание; он удаляется с directory sync, используется предшественник. Полный неверный header не отбрасывается. После успешного восстановления старые сегменты, покрытые устойчивым checkpoint, удаляются.

## Recovery и повреждения

Перед записью данных весь активный журнал проверяется первым проходом. UUID должен совпадать с основным файлом и identity. Журнал обязан покрывать LSN корректных metadata: корректный, но обрезанный префикс не может затереть более новый commit. Для сегмента после checkpoint требуется сохраненный основной файл с границей не ниже его previous commit LSN.

Второй проход применяет только полные группы с корректным COMMIT. Полные образы восстанавливают частично записанные страницы. После redo выполняются data sync, проверка LSN/UUID и целостности дерева, затем удаление неподтвержденного хвоста и WAL sync. Сбой самого redo оставляет журнал для повторного восстановления.

Неполный header/body на физическом EOF и полные образы без COMMIT считаются неподтвержденным хвостом. Полностью записанная record с неверной CRC, неправильным порядком LSN/ID или структурой дает KD3001. Это консервативная остановка с диагностикой, включая поврежденный полный хвост незавершенной транзакции. Автоматическая доступность при любом torn tail не обещается. Нельзя считать такую диагностику успешным recovery или исправлять повреждение на единственной копии.

CRC32C обнаруживает случайные повреждения и не является криптографической защитой. Неизвестная версия data format дает KD2009; запрещено молча выбирать более старый header, скрывая неизвестный формат.

## Что именно проверяется

- Ошибка до и после каждой I/O операции короткого commit и recovery, включая сохранение перед ошибкой sync.
- Short/zero writes, заполнение диска, ошибки чтения/записи/sync/resize.
- Потеря несинхронизированных записей, частичная сохранность, изменение порядка сохранения независимо в data и WAL.
- Неизменяемые подтвержденные sentinel-записи, атомарность группы insert/update/delete, повтор recovery и проверка дерева.
- Ошибка до/после каждой операции lifecycle checkpoint на реальных временных файлах, восстановление после прерванного header.
- SIGKILL отдельного процесса после полученных acknowledgements и во время частых ротаций.

Симулятор предполагает, что успешно синхронизированные данные и длина файла сохраняются, чтение работает согласно контракту ОС, а filesystem соблюдает file/directory sync. Несинхронизированные записи могут исчезнуть, быть частичными и переставленными. SIGKILL сохраняет page cache ОС и не эквивалентен отключению питания. Непредсказуемый контроллер диска, повреждение уже синхронизированных блоков, сетевые файловые системы и реальные отключения питания этим отчетом не сертифицированы.
