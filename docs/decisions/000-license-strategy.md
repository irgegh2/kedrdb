# Лицензионная стратегия KedrDB

Дата: 9 октября 2026 года. Статус: **выбор принят пользователем и применен к проекту**. Неизмененный официальный текст Apache 2.0 находится в [LICENSE](../../LICENSE), Cargo metadata и SPDX-заголовки указывают Apache-2.0. См. записи D003–D004 в [журнале решений](../DECISIONS.md).

## Цель

Построить большую самостоятельную компанию вокруг KedrDB. Первая версия начинает с небольших приложений; долгосрочная цель — широкое распространение и расширение продукта.

## Принятый выбор

Открытый серверный движок под Apache License 2.0. Платные продукты вокруг движка: управляемый сервис KedrDB Cloud, эксплуатация, резервные копии и восстановление как услуга, обновления, поддержка, интеграции и корпоративные средства управления.

Cloud — будущий отдельный продукт. Его создание не входит в минимальную 1.0 серверного движка.

## Почему этот выбор

1. Позволяет свободное использование и интеграцию, включая коммерческие приложения, при соблюдении условий лицензии.
2. Наличие открытого кода и стабильных правил дает пользователю возможность изучить продукт и самостоятельно развернуть его. Ожидаемый выигрыш в доверии и распространении — наша бизнес-гипотеза, а не гарантия.
3. Можно строить коммерческие услуги и отдельную платформу управления, сохраняя открытый движок.
4. Есть сопоставимый пример: ClickHouse использует Apache 2.0 и развивает облачный продукт. Это пример совместимости моделей, а не доказательство, что такая лицензия сама обеспечит успех KedrDB.

## Осознанная цена выбора

Другие компании смогут копировать код, делать закрытые изменения и продавать собственные сервисы с соблюдением Apache 2.0. Наш бизнес должен выигрывать качеством продукта и услуги, удобством, поддержкой и брендом.

Apache 2.0 не предоставляет права на товарные знаки проекта. Защита бренда и выбор лицензии кода — отдельные задачи; регистрация имени KedrDB пока не выполнена.

Разрешения на уже опубликованные версии Apache 2.0 нельзя рассматривать как временные: лицензия содержит безотзывный grant. Позднее изменение условий новых версий не забирает разрешения, уже выданные на старый код. Возможность изменения будущих условий также зависит от прав на принятые сторонние contributions.

Если главным бизнес-требованием станет запрет конкурентам предлагать хостинг нашего кода без договора, Apache 2.0 этому требованию не соответствует. Такой выбор нужно сделать до публичного распространения. Сейчас рекомендация исходит из приоритета широкого распространения открытой СУБД.

## Разделение продуктов

| Компонент | Рекомендуемая модель |
|---|---|
| Серверный движок, необходимые драйверы и базовые инструменты | Открытый код, Apache 2.0 при проверенной совместимости зависимостей |
| Управляемый хостинг и обслуживание | Платная услуга |
| Поддержка и внедрение | Платные услуги |
| Отдельная облачная панель, billing и корпоративное управление | Отдельный продукт; условия определяются при его создании |

Использование Apache-кода в отдельном коммерческом продукте не отменяет требований сохранения лицензии и уведомлений. Для зависимостей действуют их собственные условия.

## Применение и оставшиеся вопросы

LICENSE, README, Cargo metadata и новые исходники оформлены. Лицензия применяется к собственному коду, скриптам и документации проекта; сторонние материалы сохраняют свои условия. На текущем этапе внешних Cargo-зависимостей нет. При их добавлении проверяем условия отдельно.

Перед внешним распространением определить правообладателя, порядок contributions и бренд. Имя юридического лица и регистрацию товарного знака не придумываем; Apache License не требует создавать фиктивный NOTICE. Если появятся сторонние компоненты с уведомлениями, их сохраняем согласно их условиям.
