# ADR 001: граница хранения и модель отказов

Дата: 9 октября 2026 года. Статус: **рабочее техническое решение**. Интерфейс и начальный harness реализованы; перечисленные расширения остаются будущей работой.

## Границы подсистем

Текущий workspace состоит из трех crates:

- `kedr-core`: типизированные ошибки и файловый ввод-вывод; далее страницы, деревья, WAL, транзакции и каталог.
- `kedr-testkit`: симулятор одного файла, расписание ошибок, воспроизводимый генератор операций и испытание падения процесса. Не зависимость production CLI.
- `kedr`: диагностическая CLI; далее сервер, SQL, executor и протокол по мере появления кода.

Направление будущих вызовов: protocol → SQL/план → executor → transaction/catalog → storage/WAL → StorageIo. Сеть и parser не получают доступ к записи файлов. Изменение страниц принадлежит транзакции; flush разрешает WAL. Пустые реализации SQL/WAL, которые возвращали бы успех, не создаются.

Rust 1.94.1 закреплен в rust-toolchain.toml; edition 2024. Cargo.lock хранится в Git. Внешних Cargo-зависимостей пока нет; локальные crates — Apache 2.0. `unsafe_code = forbid` применяется ко всем текущим crates. Обновление toolchain или добавление зависимостей — отдельное изменение с проверками и записью причины.

## Контракт StorageIo

`read_at` и `write_at` могут вернуть меньше запрошенного. `read_exact_at`/`write_all_at` повторяют прерванные операции и обрабатывают частичный прогресс. Чтение нуля байт при непустом запросе означает EOF; запись нуля — ошибку отсутствия прогресса. Неверный диапазон проверяется до вызова backend. Ошибка может оставлять частично измененные данные или буфер; эти helpers не обеспечивают атомарность.

`set_len` изменяет длину. `sync` запрашивает устойчивость данных и метаданных этого файла через `File::sync_all`. Это не синхронизация каталога, не доказательство корректности накопителя при потере питания и не подтверждение транзакции. `len` возвращает текущую видимую длину. Backend владеет file descriptor, не открывает его в append-режиме и использует позиционный I/O без общего курсора.

`create_new` не перезаписывает существующий файл; `open_existing` не создает и не обнуляет его. Владение каталогом одним серверным процессом, блокировка каталога и синхронизация родительских каталогов нужны до реализации recovery. В этапе 1 многопроцессный доступ к базе не поддерживается: самой базы пока нет.

Коды KD1001–KD1009 фиксируются в ядре. Текст ошибки ОС может отличаться между системами; клиентский код должен ориентироваться на диагностический код. Коды SQLSTATE появятся при реализации SQL/protocol.

## Реализованная модель тестов

MemoryStorage хранит видимое и устойчивое состояния одного файла, включая длину. Успешный sync копирует видимое состояние в устойчивое. Crash восстанавливает последний sync целиком. Файл ограничен заданным количеством байт, диапазоны проверяются до выделения памяти; ошибки превышения лимита не изменяют файл.

FaultIo задает сбои по положительным уникальным номерам вызовов: короткое чтение/запись, нулевой прогресс, Interrupted и другие I/O errors, ошибка sync **до** сохранения и ошибка **после** реального сохранения. Следовательно, ошибка sync сама по себе не определяет, какая версия переживет сбой. Trace сохраняет номер, операцию, диапазон, внедренный сбой и результат. Trace находится в RAM и ограничивается числом операций самого теста.

Seed воспроизводит выбор операций. При падении randomized test выводит seed/step. Повтор одного seed: `KEDR_TEST_SEED=42 cargo test -p kedr-testkit seeded_operations`. Эталон использует независимую разреженную BTreeMap байтов и длину; он не вызывает код MemoryStorage.

Одинаковый тест «write → sync → crash → read» запускается для исправного backend и намеренно сломанного sync, который возвращает успех без сохранения. Harness обязан обнаруживать потерю во втором случае. Дополнительно subprocess принудительно завершается SIGKILL после sync; проверяется сохраненный префикс. Несинхронизированный хвост после SIGKILL может остаться в кэше ОС, его исчезновение не предполагается.

## Что пока не моделируется

- Произвольная сохранность части **несинхронизированных** записей и переупорядочивание.
- Частично записанные секторы/страницы, битовые повреждения и delayed I/O errors.
- Несколько файлов, создание/rename/unlink, устойчивость directory entries.
- Полный объем диска во время реального WAL/checkpoint и сбой в процессе recovery.
- Потеря питания компьютера/накопителя; сертификация файловой системы.
- SQL-истории, транзакционная изоляция и конкурентная запись.

Эти расширения обязательны в этапах 2–4 для доказательства хранения и транзакций. Положительный тест этапа 1 не объявляет СУБД crash-safe.

## Проверки платформ

Локально доступны macOS ARM64 и закрепленный Rust. CI описывает Ubuntu 24.04/x86_64 и macOS 15/ARM64 с format, clippy, debug/release tests и CLI smoke check. Файл workflow не означает исполненный Linux run. До закрытия платформенного условия этапа 1 нужен сохраненный успешный Linux результат.
