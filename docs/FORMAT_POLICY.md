# Форматы, обновление и откат бинарного файла

10 октября 2026, этап 7. Версия программы (`0.1.0 development`) отдельно от форматов.

| Формат | Текущая версия | Проверка |
|---|---|---|
| identity KEDRID01 | 1 | 32 байта, ID/CRC/reserved |
| data metadata | 2 | Две 16-КиБ копии, identity/LSN/flags/CRC; legacy version 1 отдельно |
| страницы B+ tree | 1 | 16 КиБ, тип/границы/CRC/полный граф |
| WAL segment/record | 1 | Identity, segment, LSN, COMMIT boundaries/CRC |
| SQL catalog / typed row | 1 | KEDRSQL1, explicit tags/lengths/limits |
| SQL export | 1 | Header/footer, ограниченный canonical dialect |
| SQL import progress | 1 | Отдельный служебный key [2], job SHA/ordinal/done под той же транзакцией |
| Backup manifest | 1 | Строгая структура, три файла, SHA-256/длины/checkpoint |
| Migration manifest | 1 | postgres-16-18-bounded-v1, сохраненный snapshot |
| Metrics JSON | 1 | Версионированный TEXT payload, отсутствующие samples — null |

Изменения этапа 7 не меняют data/page/WAL/catalog/row format. На **завершенной** копии проверены чтение и запись бинарным файлом этапа 6, затем открытие этапом 7. Прогресс импорта — служебный ключ, не бизнес-строка. Старый stage6 binary не знает новых `.import-incomplete`/`.migration-incomplete` markers: его **запрещено запускать на незавершенном импорте**. До публичной alpha обратная совместимость всех development snapshots не обещана.

Неизвестные metadata/page/WAL версии и flags приводят к отказу. Нельзя выбрать вторую metadata copy, скрыв неизвестную версию первой. Backup manifest с новым форматом отклоняется до изменения destination. На будущем новом физическом формате старый бинарный файл должен отказать; откат потребует старой проверенной backup или отдельного обратного конвертера. Просто заменить binary нельзя.

Порядок обновления:

1. Остановить всех писателей/сервер, проверить старую backup через restore в новый путь.
2. Сохранить старый binary, его SHA-256, версию/commit и исходный data каталог.
3. На **копии** открыть новый binary, проверить integrity, весь canonical SQL и реальные запросы приложения.
4. Если формат поддерживается без конвертации — переключить одну рабочую копию. При новом формате выполнять только отдельный проверенный мигратор, который не меняет оригинал.
5. До новых записей возможен возврат на старую сохраненную копию. После новых записей сохраненный старый backup уже устарел: автоматический откат запрещен без проверенного переноса новых изменений.

Unknown-format, wrong-version/hash/missing-WAL проверки входят в тесты. Обратная совместимость на завершенном формате и перенос Linux backup→macOS закреплены отдельными acceptance сценариями; это не обещание чтения любой будущей версии.
