10 октября 2026. Статус: начат; получены исходный baseline и две оптимизации. Полная приемка этапа впереди.

Проверен KedrDB commit `39b7742b97f6189f8d62ab0b669179f317e1b00c` против postgres (PostgreSQL) 18.6. Скрипт сохранен вместе с результатами; SHA-256 исходников и бинарных файлов, версии, настройки, порядок прогонов и аппаратные параметры — в [сводке](results/2026-10-10-stage8/baseline.json).

Медиана отдельно каждого показателя из пяти повторов. TPS — успешные логические операции в секунду; p99 включает повторы транзакции и проверку ответа.

| 8 | 78.6 | 7796.2 | 90.827 | 0.700 | 140.124 | 3.053 | 198.700 | 5.548 | 99.2× |

**Во всех 30 прогонах: ноль ошибок, полная проверка статических значений и всех подтвержденных audit events пройдена.** Итоговый stock проверяется на принадлежность подтвержденным значениям этого товара; глобальный порядок commit не восстанавливается. Отдельные correctness tests проверяют атомарность и конкурентную работу. Это ограничение явно сохранено в summary.

## Условия

- 1 000 товаров, по 100 пользователей/заказов/позиций, TEXT payload 128 ASCII bytes; те же пять таблиц, ограничения и индексы у обеих СУБД. Каждое испытание начинается с новой копии одних данных.
- 95% чтение товара по PK / 5% UPDATE stock + INSERT audit event в одной транзакции. Равномерные ключи, фиксированный seed, максимум пять попыток при serialization/deadlock; повторы входят в latency.
- По пять повторов, 1/8/32 клиента, три секунды нагрузки плюс завершение последней операции. Порядок всех 30 испытаний перемешан заранее. Каждое соединение прогрето десятью чтениями. Соединения постоянные, TCP loopback, SCRAM, psycopg 3.3.2, prepared parameters и binary results.
- PostgreSQL: fsync, synchronous_commit и full_page_writes включены; SERIALIZABLE, shared_buffers 256MB. KedrDB использует текущие WAL fsync + data fsync и сериализацию доступа. Сохранность не отключалась для ускорения.
- macOS ARM64, Apple M4, RAM 16 GiB. Точные сведения и configure flags отдельного PostgreSQL 18.6 находятся в summary/build metadata. Существующая PostgreSQL и пользовательские данные не участвуют.

## Что объясняет разрыв и что проверять дальше

По чтению исходников обнаружена лишняя работа: extended protocol в `server.rs::execute_inner` открывает обычный BEGIN даже для SELECT. На Sync выполняется COMMIT; `StorageTransaction::commit` всегда создает новый metadata checkpoint и fsync WAL/data, даже если записей не было. Чтение поэтому получает эксклюзивный режим и дисковые записи. Это подтвержденный путь выполнения, но его доля в общей задержке пока не выделена отдельным экспериментом.

Первый кандидат на оптимизацию: commit без изменений не должен писать WAL/data. Обязательны regression tests отсутствия записи/fsync при чтении, сохранности реальных записей, отмены/abort и recovery; затем тот же benchmark без смены условий. Следующие кандидаты: параллельное чтение в extended transactions, повторное выделение page cache, запросы каталога/планирование. Их эффект нельзя обещать без измерения.

## Границы и следующие проверки

Это локальная диагностика, не приемка SMALL_OLTP_V1 и не рыночный рейтинг. Набор маленький, короткий и закрытый; нет hard limits 4 CPU/512 MiB, cold cache, данных больше RAM, насыщения с p99≤20мс, длительного обслуживания, MySQL/MariaDB и независимого оборудования. Python/GIL может ограничивать скорость клиента. RSS отдельных PostgreSQL процессов нельзя складывать как PSS: shared memory будет посчитана несколько раз. CPU/RSS сохранены как вспомогательные данные, без вывода о преимуществе памяти. Во время Kedr испытаний отдельный PostgreSQL остается запущенным без клиентской нагрузки.

До приемки этапа нужны полный протокол [BENCHMARKS](../BENCHMARKS.md), профили, оптимизации с повторной проверкой корректности, большие/cold данные, длительное обслуживание и отдельные измерения Studio. Процент этапа не вычисляется из числа коротких прогонов.

## Оптимизация 2: кэш страниц заполняется по мере чтения

Commit `58f1e986bde81e60e50690ab77f2d13617ca4e2f`. Прежний PageStore каждый раз создавал и обнулял все frames в пределах cache budget, даже для запроса нескольких страниц. Новый вариант резервирует тот же bounded budget, создает frames только по мере загрузки страниц, переиспользует свободный frame после ошибочного чтения и при достижении лимита сохраняет прежнее вытеснение. Формат страниц, WAL и подтверждение реальной записи не менялись. `allocated_bytes` учитывает всю зарезервированную емкость; это не утверждение о снижении лимита памяти.

## Оптимизация 3: связанный пакет пути запросов

Source commit `ee6a31f90fa065f0831ab6c5fdb2d2062c87883b`. Пакет по запросу пользователя D041:

- CRC32C slicing-by-8 со статической таблицей вместо побайтовой цепочки; полином/формат неизменен, без unsafe и новых зависимостей.
- Поиск ключа декодирует каждый посещенный узел один раз и переносит найденное значение; проверки CRC, структуры, уровней и глубины сохранены.
- Parse сохраняет SQL AST; Execute использует его повторно, но разрешает имена/типы/ограничения по текущему каталогу. Изменившаяся форма результата отклоняется сервером.
- Одиночный unlimited read-only Execute, непосредственно за которым уже получен пустой Sync, использует shared read snapshot. Lookahead не ждет будущего сообщения. Нет Sync, есть Flush, другой Execute, suspension или явная транзакция — прежние границы.
- Ограниченные reader/writer buffers и очередь четырех кадров сокращают мелкие сетевые отправки. Flush/Sync/Query/ошибка/конец доступной очереди отправляют ответ с deadline 5 секунд.

Сохранность реальных записей не ослаблена: WAL.sync → применение страниц → data.sync → подтверждение. Профиль до изменений показал повторное декодирование страниц и ожидание блокировок; инструментированные результаты [до](results/2026-10-10-stage8/bundle/profile-before-summary.json) не смешиваются со сравнительным тестом. ### Оставшиеся ограничения после пакета

[Профиль после](results/2026-10-10-stage8/bundle/profile-after-summary.json) — отдельный инструментированный запуск, не дополнительное сравнительное измерение. В top-of-stack выделяется `__fcntl` именно в стеке `WAL::commit → FileStorage::sync`/сохранение данных. Декодирование узлов и метаданных также остается. Суммы ожидания 32 потоков не интерпретируются как доля wall time; sample и его TPS не смешиваются с основной таблицей. [Сырой профиль](results/2026-10-10-stage8/bundle/profile-after-sample.txt.gz), [driver](results/2026-10-10-stage8/bundle/profile-driver.py).

Медиана CPU сервера на завершенную операцию в обычных сравнительных прогонах: 1.684 → 0.659мс / 1.785 → 0.661мс / 2.146 → 0.818мс для 1/8/32 клиентов. Это разность process CPU до/после нагрузки, деленная на число успешных операций, не клиентская latency и не изолированный hardware counter. Счетчик single_read_batches во всех прогонах равен числу нагрузочных чтений плюс warmup и 13 завершающих validation SELECT; метрика process cumulative, не все эти SELECT входят в измеряемое время.

Основные следующие направления: сокращение повторных файловых чтений и декодирования с ограниченным кэшем и корректной инвалидацией; уменьшение времени удержания writer gate; пакетное сохранение WAL нескольких commit (group commit) и отделение checkpoint от подтверждения только после проектирования сохранности/метаданных/восстановления и новых crash tests. Простое отключение sync неприемлемо: реальное сохранение записей остается частью сравнения. Равный TPS при 8 и 32 клиентах вместе с профилем показывает ограничение текущей архитектуры записи; это еще не доказательство точного вклада каждого компонента.
