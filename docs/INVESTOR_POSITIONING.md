# KedrDB: функции для MVP и проверка преимуществ

Дата: 9 октября 2026 года. Статус: **обсуждаемые продуктовые гипотезы**, не обещания реализованных возможностей. Пользователь просит самостоятельную полезную функцию ядра и планирует презентацию инвесторам после работающего MVP. Окончательная функция еще не выбрана.

## Продуктовая задача

Первая аудитория — разработчики магазинов/учета. Им приходится разбираться, выполнился ли заказ после сетевого сбоя, предотвращать дублирование записи, проверять массовые изменения и исправлять ошибки без потери чужих последующих изменений. Эти боли надо подтвердить разговорами с независимыми командами: сейчас это гипотезы.

Предсказуемые ресурсы, надежное восстановление и скорость остаются инженерными требованиями. Сами по себе такие обещания не доказывают преимущество нового движка. Основной MVP должен показывать завершенную полезную операцию и сравнение с существующим способом ее выполнения.

## Кандидаты на конкретную функцию

| Функция | Демонстрация на магазине | Что требуется от ядра | Предварительный приоритет |
|---|---|---|---|
| Безопасный повтор транзакции | Ответ на заказ потерян; тот же номер операции возвращает сохраненный исход, второй заказ/списание не возникает | Атомарный durable operation ledger, проверка совпадения запроса, recovery и доступ по ID | Первый кандидат для MVP после базовых транзакций |
| Репетиция изменения | До применения массовой смены цен видны точные затронутые строки и нарушения ограничений; изменившийся исходный набор блокирует устаревшее применение | Приватное состояние/snapshot, фиксируемый read/write set и проверяемая привязка к исходным данным | Второй кандидат, сильное визуальное демо |
| Отмена конкретной подтвержденной операции | Вернуть ошибочную смену цен, сохранив новые заказы; конфликтующие изменения перечислены, а не перезаписаны | Before/after images, история, dependency/conflict checks, повторная проверка FK/unique | Позже: существенно сложнее обычного rollback |
| Подписка на результат SQL | Остаток/список товаров обновляется в приложении при изменении данных без постоянного SELECT | Durable change stream, snapshot boundary, resume token, delta semantics | Позже; произвольные join/aggregates значительно увеличивают сложность |
| Проверяемые бизнес-правила транзакции | Указанное правило остатков/сумм автоматически проверяется перед commit, включая конкурентные изменения | Ограниченный язык инвариантов, dependency locks и корректное incremental validation | Исследование; начать с конкретного правила пилота |

Названия здесь описательные. Они не являются выбранными торговыми марками или готовым SQL API. Оценки приоритета — инженерное суждение; календарные обещания пока не даются.

## Первый рекомендуемый кандидат: безопасный повтор

Приложение передает стабильный operation ID и описание операции. KedrDB атомарно сохраняет изменение данных и небольшой итог операции. После disconnect/restart повтор того же ID с тем же запросом возвращает сохраненный итог или статус, не выполняя изменение второй раз. Тот же ID с другими параметрами — явная ошибка.

Пример: заказ ORD-427 уменьшает остаток на 2 и добавляет заказ/позиции. Сервер сохраняет commit, но ответ теряется. Приложение повторяет ORD-427; строка заказа одна, остаток уменьшен на 2 один раз. Демо принудительно обрывает соединение до/после durable point и перезапускает базу; проверка идет по данным, а не по красивому сообщению UI.

Нужно определить до реализации:

- Scope ID: база/пользователь, формат, максимальная длина; право прочитать результат.
- Канонический fingerprint операции, параметры и версия схемы; защита от неоднозначной повторной команды.
- Максимальный размер сохраняемого результата; недетерминированные функции и несколько statements.
- Состояния pending/committed/failed/unknown и поведение одновременных повторов.
- Срок хранения истории и tombstones. После удаления информации об ID нельзя продолжать обещать бесконечную дедупликацию.
- Политика ошибок до commit; гарантия фиксируется отдельно для успешно подтвержденных операций и сохраненных отказов.

Граница: эффект гарантируется в нашей базе и в заданном окне хранения. Отправка письма, списание во внешнем платежном API и другие внешние действия требуют собственного протокола; повтор SQL не обеспечивает их однократность. Это не обещание «exactly once для всего мира».

Критерии MVP: одно изменение при двух конкурентных повторах; сохранение результата после падения; mismatch ID/параметров отклоняется; понятная история в программе управления; измеренный overhead WAL/памяти/задержки. Сравниваем с качественно реализованной транзакционной таблицей idempotency в PostgreSQL, а не с заведомо ошибочным приложением без нее.

## Более сильная общая концепция: проверяемый пакет изменения

Возможная последующая комбинация: **предпросмотр → применение с operation ID → сохраненный итог → ограниченная отмена с проверкой конфликтов**. Это единая функция ядра, которую программа управления показывает как понятный процесс. Для новой операции можно объяснить, какие строки меняются, проверить применимость к текущему состоянию и получить устойчивый ответ на повтор.

Первая версия предпросмотра может быть консервативной: любая релевантная смена исходного состояния требует повторной репетиции. Не обещаем мгновенный clone большой базы, прогноз будущей скорости или безопасную отмену любого изменения. Отмена создает новую компенсирующую транзакцию; она не стирает историю и не обходится без проверки зависимостей.

Это кандидат на отличие в продукте и workflow. Сочетание еще не проверено на спрос, overhead и конкурентную уникальность. Полная комбинация не добавляется автоматически в обязательный выпуск 1.0: сначала выбираем и проверяем первый маленький контракт.

## Аналоги и честное сравнение

- [TigerBeetle](https://docs.tigerbeetle.com/coding/reliable-transaction-submission/) использует ID для надежной повторной отправки объектов/операций. Поэтому встроенную идемпотентность нельзя объявлять неизвестным индустрии изобретением. Наш кандидат — удобный контракт для поддерживаемых SQL-транзакций первого приложения.
- [Neon](https://neon.com/blog/api-track-schema-changes) предлагает branch/schema diff для проверки изменений. Само наличие веток или schema diff не создаст уникального преимущества KedrDB.
- [Dolt](https://github.com/dolthub/dolt) предоставляет SQL-базу с версиями, branch/merge/revert. История и отмена также имеют действующие аналоги.
- [Materialize SUBSCRIBE](https://materialize.com/docs/sql/subscribe/) стримит изменения результатов запросов. «Живой SQL» нужно сравнивать с существующими реализациями, включая их границы.
- [PostgreSQL memory settings](https://www.postgresql.org/docs/18/runtime-config-resource.html) управляют buffers и памятью операторов; work_mem не равен общему пределу памяти всех запросов. Наш общий budget/admission control — проверяемая архитектурная гипотеза; она сравнивается с разумно настроенным PostgreSQL и системными лимитами.

Обзор не является исчерпывающей проверкой рынка или патентной новизны. В презентации нельзя писать «такого ни у кого нет» на основании этих нескольких источников.

## Программа управления

Пользователь подтвердил направление: собственная быстрая и удобная программа управления KedrDB. Она должна показывать преимущества ядра: соединение/таблицы/SQL, результат и статус операции, предпросмотр изменений, диагностику и восстановление по мере появления этих функций.

Кандидат первого демо: открыть магазин, создать заказ, оборвать ответ, повторить ID и показать единственный заказ и правильный остаток. Для полноценной программы нужны отдельные UX-тесты, время старта/реакции и удобство против pgAdmin; красивый макет не доказывает работу ядра.

Прототип UI относится к этапам протокола/инструментов, после реального API. Framework и название пока не выбираем. Список обязательных GUI-функций/сроки MVP остаются открытыми.

## Материалы к встрече с инвестором

- Работающее приложение и воспроизводимое демо выбранной функции, включая отказ.
- Реальные пилоты: проблема, альтернативный путь, причина использования, готовность платить — пока не получены.
- Benchmark с одинаковыми гарантиями, версиями и оборудованием; overhead новой функции отдельно.
- Затраты внедрения и эксплуатации: клиентский код, параметры, recovery/restore; наблюдения пилота отдельно от наших предположений.
- Честные границы SQL, объема, конкурентной записи и совместимости.
- Текущий инженерный статус: этап 1 пройден; страницы этапа 2 начинаются. SQL и перечисленные новые функции пока не реализованы.

Рабочая фраза для обсуждения: «KedrDB помогает SQL-приложению безопасно проводить изменения: проверить последствия, выполнить с проверяемым ID и разобраться с повтором после сбоя». Публичное утверждение возможно только после реализации точного контракта, измерений и пилотной проверки.
