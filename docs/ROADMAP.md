# Путь до версии 1.0

Дата плана: 9 октября 2026 года. Статус: этап 1 пройден; начинаем этап 2. Выпуск 1.0 еще не готов.

Прогресс: [PRODUCT.md](PRODUCT.md), [отчет 00](milestones/00.md), [отчет 01](milestones/01.md). Первая задача, название и лицензия подтверждены пользователем. Технический профиль и предварительный PostgreSQL baseline подготовлены. Рыночная проверка и проверка публичного имени открыты. Важные ответы сохраняются в [DECISIONS.md](DECISIONS.md).

## 1. Какой продукт мы строим

Самостоятельную серверную SQL-СУБД на Rust. Хранение, индексы, транзакции и выполнение запросов принадлежат нашему движку. Готовые библиотеки допустимы для разбора SQL, сетевого протокола, криптографии, конфигурации и тестирования. Встраивание SQLite или PostgreSQL под новым названием не достигает цели этого проекта.

Рабочая гипотеза: небольшие прикладные сервисы — например, каталог товаров, учет заказов или внутренний инструмент — с данными порядка 1–10 ГБ и умеренным количеством записей. База работает на одном узле, имеет понятную установку, ограниченный расход памяти и проверяемые транзакционные гарантии.

Эта гипотеза выбрана из исходного желания сделать систему типа PostgreSQL. До подтверждения этапа 0 это не окончательное решение о рынке. Аналитическая или встраиваемая база потребует другой архитектуры и нового плана.

Первое предполагаемое преимущество: меньше сложности при установке и обслуживании, небольшой расход ресурсов, хорошая задержка простых индексных запросов. «Быстрее PostgreSQL во всем» не является проверяемой целью. Преимущество должно быть полезно конкретному пользователю и подтверждено на его задачах.

Дополнение пользователя: обязательное итоговое сравнение с разными базами и движение к первому месту по скорости. Поэтому до начала реализации фиксируем категорию, набор конкурентов и метрику лидерства. Промежуточные измерения направляют разработку; итоговый сравнительный отчет выполняется на release candidate после пилотов. Подробные правила — в BENCHMARKS.md.

## 2. Что должно входить в минимальную рыночную 1.0

| Область | Минимум для выпуска | Чем подтверждается |
|---|---|---|
| Установка | Один серверный бинарный файл, конфигурация, инструкции для Linux, диагностируемый старт | Установка на чистой машине по документации |
| Хранение | Собственный бинарный формат, страницы, контрольные суммы, буферный кэш, B+ tree | Property-тесты и проверка целостности |
| Транзакции | Автоматическая транзакция на команду, BEGIN/COMMIT/ROLLBACK, явно описанная изоляция | Истории конкурентных операций и тесты отката |
| Сохранность | Подтверждение COMMIT после устойчивой записи журнала, восстановление после сбоя | Управляемые сбои и журнал подтвержденных транзакций |
| Таблицы | CREATE TABLE, DROP TABLE, простое ADD COLUMN; постоянный каталог схем | Перезапуск, откат DDL, изменение схемы |
| Типы | INT, BIGINT, TEXT, BOOLEAN, NULL с явными правилами диапазонов и сравнений | Граничные и дифференциальные SQL-тесты |
| Ограничения | PRIMARY KEY, NOT NULL, UNIQUE, простые внешние ключи | Невозможность записать некорректные данные |
| Запросы | INSERT/SELECT/UPDATE/DELETE, параметры, WHERE с AND и сравнениями, ORDER BY, LIMIT, COUNT(*), простой INNER JOIN | Сравнение поддерживаемого подмножества с PostgreSQL |
| Индексы | Первичный B+ tree и вторичные одноколоночные индексы | Проверка согласованности индексов после записи и восстановления |
| Подключение | Проверенное подмножество PostgreSQL wire protocol, psql и один выбранный драйвер | Тесты реального клиента с указанной версией |
| Безопасность | Аутентификация, TLS для удаленного доступа, пределы запросов и соединений | Негативные сетевые тесты и проверка конфигурации |
| Эксплуатация | Логи, метрики, таймауты, отмена запросов, штатная остановка | Нагрузочные и операционные сценарии |
| Восстановление | Проверенный backup/restore, SQL-экспорт и импорт для переноса данных | Восстановление на другой машине |
| Поддержка | Документация ограничений, лицензия, сборки, порядок сообщения об ошибках | Пилотные пользователи и чек-лист выпуска |

Ограничения первой версии:

- Один узел, один процесс сервера, один активный писатель. Читающие транзакции могут выполняться совместно; запись блокирует чтение. Эта модель подходит только для выбранной умеренной нагрузки.
- Одна логическая база на процесс; разделение приложений — отдельными экземплярами.
- Первичная производственная платформа — Linux x86_64 с локальным файловым хранилищем. macOS ARM64 — среда разработки до отдельного подтверждения надежности.
- Целевой проверяемый объем — до 10 ГБ. Это план тестового диапазона, не уже установленная характеристика продукта.
- В каждой таблице необходим явно заданный первичный ключ. В 1.0 он одноколоночный типа BIGINT; автоматическую выдачу значений можно включать только после отдельного решения и тестов.
- Простой внешний ключ с немедленной проверкой и поведением NO ACTION. Каскады и отложенная проверка откладываются.
- Нет репликации, автоматического переключения на резервный узел, распределенных транзакций и шардирования.
- Нет полного набора SQL PostgreSQL, всех его типов, расширений и системных каталогов. Нет обещания, что любой ORM или pgAdmin заработает.
- Определяются явные пределы строки, транзакции, запроса, результата, времени удержания блокировки и памяти. Превышение дает понятную ошибку, а не аварийное завершение.
- Backup первого выпуска может требовать обслуживания в режиме остановленной записи. Это приемлемо только если пилотные пользователи согласны с таким окном.

Часть ограничений может оказаться неприемлемой для рынка. Тогда меняется состав продукта до объявления 1.0, а не после продажи.

## 3. Как пользоваться этапами

У каждого этапа есть задачи, артефакты и условия перехода. Галочка означает «есть проверяемое доказательство», а не «код выглядит законченным».

Можно параллельно вести документацию, сборки, клиентский протокол и поиск пилотов. Зависимость хранения, восстановления и транзакций остается последовательной. Оптимизация не отменяет повторное прохождение тестов корректности.

Для каждого этапа создаем отчет `docs/milestones/NN.md`: commit, что реализовано, команды проверок, среда, результаты, известные дефекты, принятые ограничения и решение о переходе. Для каждого изменения, влияющего на формат, транзакции или сеть, записываем отдельное архитектурное решение в `docs/decisions/`.

Прогресс этапов 0–1 отражен ниже и в отчетах; этапы 2–10 остаются будущими задачами. Галочки выбора требований не означают реализацию этих требований в нашем движке.

## Этап 2. Страницы, записи и B+ tree

Результат: внутреннее хранилище с индексом, которое переживает штатный перезапуск. Гарантии аварийного восстановления еще не объявляются.

- [ ] Реализовать страницы фиксированного размера, ограниченное кодирование строк и слотов, обработку свободного пространства.
- [ ] Определить endian, диапазоны чисел, кодирование UTF-8 и правила NULL. Не использовать сериализацию Rust struct как дисковый контракт.
- [ ] Реализовать ограниченный буферный кэш, pin/unpin страниц и вытеснение.
- [ ] Реализовать B+ tree: поиск, диапазон, вставка, разделение узлов, удаление, слияние или явно обоснованную альтернативу.
- [ ] Реализовать вторичный индекс с парой «значение, первичный ключ», включая дубликаты и NULL.
- [ ] Реализовать выделение и освобождение страниц без повторного использования живых страниц.
- [ ] Определить ограничение строки первой версии. Рабочая гипотеза: кодированная строка до 8 КиБ; overflow-страницы включать только при необходимости пилота.
- [ ] Сделать команду проверки дерева, страниц, ссылок и порядка ключей.
- [ ] Создать файл больше доступного кэша и убедиться, что движок не загружает всю базу в память.

Условие перехода:

- [ ] Случайные вставки/обновления/удаления/поиски совпадают с эталонной моделью.
- [ ] Проверены границы страниц, дубликаты, минимальные/максимальные ключи, удаление последней строки, повторное заполнение и перезапуск.
- [ ] Поврежденные заголовки и страницы дают диагностируемую ошибку; файл не «чинится» молча.

- [ ] Предварительная кампания: минимум 100 seeds по 10 000 операций без расхождений, с сохранением всех найденных ошибок в регрессионные тесты.

Артефакты: хранилище, инструмент integrity-check, отчеты property-тестов и профиль памяти.

Ориентир: 3–6 недель.

## Этап 3. Журнал и восстановление после сбоев

Результат: доказанная в заданной модели атомарность записи и сохранность подтвержденных транзакций.

Задачи:

- [ ] Реализовать WAL: длина, тип, transaction id, последовательный номер, контрольная сумма, полные образы измененных страниц и запись COMMIT.
- [ ] Запретить запись неподтвержденных изменений в основной файл данных: приватный набор измененных страниц и ограничение его памяти.
- [ ] Зафиксировать порядок: журнал изменений и COMMIT → устойчивая синхронизация → публикация → ответ клиенту.
- [ ] Различать логическое завершение, устойчивый commit и отправку ответа клиенту.
- [ ] Ввести безопасный режим для неопределенного исхода ошибки fsync: остановка записи и восстановление вместо продолжения на сомнительном состоянии.
- [ ] Реализовать повторяемый redo завершенных транзакций; неполный хвост игнорировать только по документированному правилу.
- [ ] Различать неполный хвост последнего сегмента и повреждение внутри журнала. Повреждение подтвержденных записей не скрывать.
- [ ] Реализовать checkpoint, синхронизацию файла и метаданных каталога, управление сегментами WAL и безопасное удаление старых сегментов.
- [ ] Защитить метаданные checkpoint от частичной записи, например двумя версионированными копиями с контрольными суммами.
- [ ] Проверить короткую запись, заполнение диска, ошибки чтения/записи/синхронизации, перестановку несинхронизированных записей, обрыв WAL и частичную запись страницы.
- [ ] Проверить сбой во время восстановления и во время checkpoint.
- [ ] Описать, какие гарантии зависят от ОС и накопителя; устойчивое сохранение при отключении питания испытывать отдельно от SIGKILL.

Условие перехода:

- [ ] Для каждого шага дискового ввода-вывода в коротких сценариях пройдены управляемые сбои.
- [ ] После восстановления каждая транзакция применена целиком или отсутствует; таблицы и индексы согласованы.
- [ ] Все транзакции, на которые тестовый клиент получил успешный ответ COMMIT, присутствуют после восстановления.
- [ ] Транзакция без полученного ответа может присутствовать или отсутствовать; тесты не ошибочно требуют ее отсутствия.
- [ ] Повторное восстановление и повторное применение журнала не меняют правильный результат.
- [ ] Предварительная расширенная кампания: минимум 10 000 случайных точек отказа без необъясненных расхождений. Это дополнение к детерминированным проверкам, не доказательство всех возможных отказов.

Артефакты: WAL, recovery, crash harness, отчет с seeds и перечнем точек отказа, спецификация durability.

Ориентир: 4–8 недель. Один из главных источников неопределенности сроков.

## Этап 4. Транзакции и конкурентные соединения

- [ ] Запретить изменение в READ ONLY и повышение разделяемой блокировки до эксклюзивной.
- [ ] Сделать очередь ожидания с защитой от голодания, таймаутом и отменой.

- [ ] Определить поведение ошибки SQL внутри явной транзакции: aborted до ROLLBACK; никаких частичных продолжений.
- [ ] Откатывать незавершенную транзакцию при разрыве соединения и освобождать ресурсы.
- [ ] Задать предел времени жизни транзакции и idle-in-transaction timeout.
- [ ] Проверить лимит памяти приватных страниц и согласованное поведение отказа.
- [ ] Проверить историю двух клиентов: конфликтующие записи, чтение во время записи, rollback, cancel и disconnect.

Условие перехода:

- [ ] Истории поддерживаемых транзакций эквивалентны последовательному порядку; нет грязного чтения и потерянных обновлений.
- [ ] Долгий клиент не удерживает блокировку бессрочно после отмены или разрыва соединения.
- [ ] Ошибки и аварии не оставляют частично измененный каталог или индекс.
- [ ] Пройдены стресс-тесты с 1, 2, 8 и 32 клиентами, включая отмены и реконнекты.
- [ ] Есть отчет о задержках ожидания блокировки: ограничение одного писателя видно пользователю и измерениям.

Артефакты: transaction manager, тесты конкурентных историй, таблица гарантий изоляции.

Ориентир: 3–6 недель.

## Этап 5. SQL и работающая прикладная модель

Результат: реальное приложение может описать свои таблицы и выполнять поддерживаемые операции.

Задачи:

- [ ] Выбрать готовый SQL-парсер или собственный небольшой парсер; документировать поддерживаемый диалект.
- [ ] Отделить parser, разрешение имен и типов, логический план, физический план и executor.
- [ ] Реализовать постоянный каталог таблиц/столбцов/индексов и его транзакционное изменение.
- [ ] Реализовать INT/BIGINT с проверкой переполнения, TEXT в UTF-8, BOOLEAN, NULL. Для первой версии сравнение текста — бинарное; отличия от колляций PostgreSQL явно описать.
- [ ] Реализовать DDL и CRUD из таблицы состава 1.0. У неподдерживаемых конструкций — явная ошибка.
- [ ] Реализовать SQL-семантику NULL, сравнения, IS NULL, AND и правила сортировки NULL.
- [ ] Реализовать первичный ключ, NOT NULL, UNIQUE и немедленные одноколоночные внешние ключи NO ACTION.
- [ ] Реализовать параметры отдельно от SQL-текста, включая NULL и проверку типов.
- [ ] Реализовать простой INNER JOIN по равенству, COUNT(*), ORDER BY и LIMIT.
- [ ] Сделать выбор между полным сканированием и индексом; добавить EXPLAIN с выбранным доступом.
- [ ] Задать лимиты памяти сортировки/соединения/результата и ошибки превышения. Внешняя сортировка включается, если нужна для целевого сценария.
- [ ] Подготовить пример магазина: товары, пользователи, заказы; цена в целых копейках, без неточной арифметики денег.
- [ ] Проверять тот же поддерживаемый SQL на PostgreSQL с согласованными типами, колляцией, порядком и изоляцией.

Условие перехода:

- [ ] Полный прикладной сценарий проходит после штатного и аварийного перезапуска.
- [ ] Минимум 1 000 вручную описанных/параметризованных SQL-сценариев и 100 000 сгенерированных поддерживаемых запросов прошли без необъясненных различий.
- [ ] Неправильные типы, неизвестные столбцы, дубликаты, NULL и переполнение проверены в том числе на пустых таблицах.
- [ ] Планировщик действительно использует индекс в объявленных сценариях; результаты совпадают с полным сканированием.
- [ ] Схема и строки не расходятся после ADD COLUMN, ошибок DDL и rollback.

Артефакты: SQL-движок, SQL_COMPATIBILITY.md, пример приложения, дифференциальный отчет.

Ориентир: 4–8 недель.

## Этап 6. Сервер, драйверы и безопасное подключение

Результат: к базе подключается обычное клиентское приложение без нашего специального клиента.

Задачи:

- [ ] Реализовать запуск, конфигурацию, каталог данных, файловую блокировку одного процесса, сигналы и штатную остановку.
- [ ] Привязка по умолчанию к loopback; рабочий порт, например 55432, не конфликтует с локальным PostgreSQL.
- [ ] Реализовать Startup, выбранную версию PostgreSQL protocol, Simple Query и сообщения результата/ошибки/статуса.
- [ ] Реализовать Extended Query: Parse, Bind, Describe, Execute, Close, Flush, Sync и восстановление состояния после ошибки.
- [ ] Реализовать параметры, необходимые OID, текстовые и используемые выбранным драйвером бинарные представления типов.
- [ ] Реализовать SCRAM-SHA-256 через проверенную библиотеку, TLS и безопасное хранение проверочных данных пароля. Не разрабатывать собственную криптографию.
- [ ] Сделать один административный аккаунт в 1.0 с явно документированным ограничением; дополнительные роли включить, если их требует пилот.
- [ ] Ограничить длину сообщения до выделения памяти, количество соединений, ожидание клиента, скорость чтения и объем результата.
- [ ] Реализовать отмену запроса с проверкой ключа сессии; отключение чужой сессии невозможно без нужного ключа.
- [ ] Реализовать минимальные запросы состояния и каталога, необходимые выбранному драйверу. Не подделывать системные каталоги обещаниями полной совместимости.
- [ ] Проверить psql и один драйвер с фиксированными версиями, например psycopg 3 либо tokio-postgres по выбору первого приложения.
- [ ] Проверить некорректные пакеты, частичные сообщения, pipeline с ошибкой, медленного клиента, EOF посередине сообщения.

Условие перехода:

- [ ] Клиент подключается, аутентифицируется, делает параметризованный CRUD и транзакцию, получает ошибку и корректно продолжает работу.
- [ ] Отмена и разрыв соединения освобождают ресурсы, не повреждая данные.
- [ ] Удаленное подключение идет с TLS; пароли не попадают в логи.
- [ ] Неподдерживаемые запросы драйвера описаны; клиентская матрица указывает проверенную версию и режим работы.
- [ ] Корпус некорректных пакетов не вызывает panic, зависание или превышение лимитов памяти.

Артефакты: сервер, интеграционные тесты драйверов, CONNECTIONS.md, матрица совместимости.

Ориентир: 3–6 недель. Протокол можно разрабатывать на заглушке параллельно SQL; приемка требует настоящего движка.

## Этап 7. Резервные копии, обслуживание и наблюдаемость

Задачи:

- [ ] Восстановление только в новый или явно пустой каталог; существующая база не перезаписывается случайно.
- [ ] Проверить восстановление на другой машине и отказ на поврежденной/неполной копии.
- [ ] Реализовать SQL-экспорт и импорт; типы, NULL, кавычки и порядок зависимостей не теряются.

- [ ] Подготовить эксплуатационные сценарии: заполнение диска, зависший клиент, неподдерживаемый формат, ошибочные права, поврежденная страница, обновление программы.

- [ ] Можно объяснить по логам отказ запуска, медленный запрос и рост WAL.
- [ ] Пройден тест обновления поддерживаемого формата и отката бинарного файла без неподтвержденного чтения нового формата.

Артефакты: backup/restore tools, runbooks, метрики, инструкции установки и обновления.

## 4. Сколько это может занять

Оценки выше предполагают одного разработчика с ИИ, регулярную работу, узкое подмножество SQL и доступ к техническому рассмотрению. Это оценки трудоемкости с низкой уверенностью, не статистика обещанного ускорения ИИ.

| Результат | Предварительный ориентир | Что этот результат означает |
|---|---|---|
| План и проектный каркас | Часы — несколько дней | Можно организованно начинать работу |
| Первый Rust-прототип | 1–3 недели | Запись, чтение и простые запросы в ограниченных условиях |
| Инженерная альфа | 3–6 месяцев при благоприятном ходе | Основные подсистемы работают, надежность еще исследуется |
| Узкая рыночная 1.0 | Примерно 6–18 месяцев; при переделках дольше | Пройдены проверки, пилоты и условия выпуска |
| Широкая замена PostgreSQL | Годы и обычно команда | Значительно более широкий SQL, экосистема, эксплуатация, масштабирование |

Пяти минут достаточно для запуска каркаса, не для подтверждения надежности. Неделя может дать интересный прототип; назвать его рыночной 1.0 можно только если действительно выполнены условия выпуска, что для описанного состава нереалистично.

После этапа 1 уточняем трудоемкость на основании первой реализованной подсистемы. После этапа 3 пересчитываем весь график по фактическим дефектам восстановления. После этапа 8 решаем, есть ли конкурентное основание продолжать выпуск именно в этой нише.

Дополнительное условие лидерства по скорости повышает неопределенность оценки 1.0. Приведенный диапазон не гарантирует первое место за этот срок. Если простая модель одного писателя не выдерживает целевой конкуренции, работа по MVCC или иной архитектуре переносится до 1.0 и график расширяется.

Если работаем эпизодически, календарный срок увеличивается. Если первый пользователь требует высокую доступность, интенсивную многописательную нагрузку, полный PostgreSQL SQL или весь pgAdmin, границы и оценки необходимо изменить.

- Несколько одновременно записывающих транзакций, мелкие блокировки, обнаружение deadlock.
- Репликация, point-in-time recovery, failover и подтвержденная модель отказов нескольких узлов.
- Более широкий SQL: выражения, OR, агрегаты, JOIN-стратегии, подзапросы, составные индексы, дополнительные типы, колляции.
- Полноценная совместимость с выбранными ORM, DBeaver и pgAdmin по их реальным каталоговым запросам.
- Онлайн backup, поточная загрузка COPY, более крупные строки и запросы сверх памяти.
- Другие производственные ОС и файловые системы с отдельной сертификацией испытаниями.
- Управляемое облако, панель управления, биллинг и высокодоступная служба.

Если пункт необходим первому платящему пользователю, он переносится в обязательный состав до выпуска с соответствующим пересчетом сроков.

## 7. Первые конкретные действия

1. Подтвердить рабочую гипотезу и первый сценарий приложения.
2. Составить PRODUCT.md и запросы PostgreSQL для исходного сравнения.
3. Выбрать и записать гарантии транзакций, дисковой записи и ограничения.

## Источники инженерных требований

- [Протокол PostgreSQL](https://www.postgresql.org/docs/current/protocol.html): сетевой контракт — отдельная подсистема.
- [Поток сообщений PostgreSQL](https://www.postgresql.org/docs/current/protocol-flow.html): параметры, extended protocol и состояние после ошибок.
- [pgbench](https://www.postgresql.org/docs/current/pgbench.html): собственные сценарии и контролируемая конкурентность для исходного сравнения.
- [Как тестируют SQLite](https://www.sqlite.org/testing.html): сбои ввода-вывода, crash simulation и независимые проверки.
- [Atomic Commit in SQLite](https://sqlite.org/atomiccommit.html): необходимость проверять частичные и переставленные записи.

Состав 1.0, пороги тестов, архитектура и сроки — наши проектные предложения, а не рекомендации этих источников или доказательства будущей надежности.
