# Предварительная архитектура

Статус: архитектурный план с частичной реализацией. Есть файловый I/O, harness, codecs, bounded cache, B+ tree, WAL/private writes/storage transactions, файловый checkpoint и локальные конкурентные сессии. Этап 3 пройден; этап 4 прошел локальную приемку, ожидается CI. SQL и сервер впереди. Решения: [I/O](decisions/001-storage-and-failures.md), [tree format](decisions/003-tree-file-format.md), [WAL](decisions/004-wal-and-private-writes.md), [сессии](decisions/005-session-workers-and-fair-locks.md). Текущие гарантии и ограничения — в [DURABILITY.md](DURABILITY.md) и [ISOLATION.md](ISOLATION.md).

## 1. Поток запроса

```text
psql / проверенный драйвер приложения
                 |
     PostgreSQL wire protocol + TLS
                 |
    Сессия, аутентификация, лимиты
                 |
     SQL parser → имена и типы
                 |
     План запроса → выполнение
                 |
    Каталог + менеджер транзакций
                 |
  B+ tree + страницы + буферный кэш
                 |
     WAL + StorageIO + checkpoint
                 |
        Локальный диск сервера
```

Разбор SQL и сетевой протокол могут использовать готовые библиотеки. Собственными остаются модель хранения, индекс, транзакционные гарантии, восстановление и исполнение запросов. Протокол PostgreSQL не делает наш сервер полноценным PostgreSQL: каталог, SQL, типы и дополнительные возможности требуют отдельной совместимости.

## 2. Модули

| Модуль | Ответственность | Ключевой контракт |
|---|---|---|
| storage | Страницы, кодирование строк, B+ tree, кэш, свободные страницы | Не публикует неподтвержденные изменения |
| wal | Журнал, контрольные суммы, COMMIT, replay, сегменты, checkpoint | Durable position определяет, что разрешено сохранять в data file |
| transaction | Блокировки, приватный write set, commit/rollback, cancellation | Атомарная видимость и отсутствие грязного чтения |
| catalog | Таблицы, столбцы, индексы и ограничения | Изменяется атомарно вместе с данными |
| sql | Parser, разрешение имен и типов, планы | Неподдерживаемая конструкция отклоняется явно |
| executor | Чтение/запись по плану, сортировка, агрегаты, join | Ограниченная память, одинаковый результат индексного/полного чтения |
| protocol | Сетевые сообщения, параметры, типы и ошибки | Ограничения проверяются до больших выделений памяти |
| server | Сессии, конфигурация, запуск, shutdown, метрики | Один процесс владеет каталогом данных |
| tools | Backup, restore, экспорт, integrity-check, диагностика | Работа по документированным состояниям сервера |

Разбиение на crates уточняется по реальному размеру модулей. Лишние публичные интерфейсы до их необходимости не создаются.

## 3. Хранение

Предлагается страничный row store с B+ tree и ограниченным буферным кэшем. Предварительный размер страницы — 16 КиБ; его надо подтвердить измерениями и зафиксировать до стабилизации формата.

Основная таблица хранится в дереве по явному первичному ключу BIGINT. Вторичный индекс хранит значение и первичный ключ. Обновление строки и всех ее индексов относится к одной транзакции.

Для первой версии предварительный предел закодированной строки — 8 КиБ. Если целевой пользователь хранит большие документы, добавляются overflow-страницы, проверки цепочек и дополнительные crash tests. Ограничение нельзя менять только в настройке без изменения тестового диапазона.

Файл содержит идентификатор формата и базы, версию, размеры и контрольные суммы. Для каждого поля определяются endian, диапазон, кодирование и допустимые значения. Ошибочные размеры проверяются до выделения памяти. Кодирование страниц не зависит от ABI Rust и расположения структур в памяти.

Метаданные checkpoint требуют защиты от частичной записи. Кандидат: две копии с поколением и контрольной суммой; восстановление выбирает корректную версию, согласованную с WAL. При неоднозначности — ошибка и диагностическая процедура.

Нужно отделять свободную страницу от страницы, которая еще принадлежит базе или требуется для восстановления. Освобождение и повторное использование входят в транзакционную модель.

## 4. Изоляция первой версии

Кандидат на простую модель первой версии — глобальная читательско-писательская блокировка:

- Autocommit SELECT держит разделяемую блокировку до окончания чтения результата движком.
- Явная BEGIN READ ONLY держит разделяемую блокировку до COMMIT/ROLLBACK.
- Явная читающая-пишущая BEGIN и отдельные изменяющие команды держат эксклюзивную блокировку до завершения транзакции.
- Переход из READ ONLY в запись отклоняется. Это исключает deadlock повышения блокировки.
- Изменения писателя хранятся в приватных страницах. Для других транзакций они невидимы.
- Ошибка команды в явной транзакции переводит ее в aborted до ROLLBACK; disconnect откатывает незавершенную транзакцию.
- COMMIT без успешной устойчивой записи не возвращает успех.

При корректном удержании блокировок такая модель обеспечивает последовательный порядок транзакций, но долгие читатели мешают записи, а писатель блокирует читателей. Таймауты, справедливая очередь, ограничение транзакции и освобождение ресурсов обязательны.

Сеть не должна удерживать блокировку бесконечно из-за медленного потребителя. Предлагается ограниченное буферизование результата до освобождения блокировки; при превышении лимита запрос получает ошибку. Потоковый результат потребует отдельного решения о времени жизни блокировки или снимка.

Выбор этой модели допускается только если она подходит первой нагрузке. При требовании лидерства под смешанной многоклиентской нагрузкой возможно потребуется MVCC уже до 1.0. Это архитектурное изменение со своими проверками видимости, версий, очистки и восстановления, а не локальная оптимизация.

## 5. Устойчивая запись и восстановление

Предварительная модель: redo-only WAL с полными образами измененных страниц и no-steal для неподтвержденных изменений.

Последовательность транзакции:

1. Проверить ограничения и сформировать приватный набор страниц, включая каталог и индексы.
2. Записать страницы в WAL и завершить запись COMMIT с проверяемыми границами.
3. Устойчиво синхронизировать необходимые файлы журнала и метаданные создания сегментов.
4. Опубликовать изменения в памяти под эксклюзивной блокировкой. Подтвержденные страницы теперь можно сохранять в основной файл.
5. Освободить транзакционные ресурсы и отправить успешный ответ.

Checkpoint сначала обеспечивает устойчивость всех нужных data pages, затем устойчиво фиксирует свою границу. Только после этого можно удалять WAL, который больше не нужен recovery или backup. Смена сегментов, создание и удаление файлов имеют собственные точки отказа.

Восстановление проверяет формат и checksum, выбирает корректную границу checkpoint и повторяет только завершенные транзакции после нее. Полные образы страниц должны устранять частичные записи data pages. Повторный replay дает тот же результат. Неполный последний хвост отличается от повреждения в середине WAL.

Неоднозначный исход fsync — отдельный режим. Сервер не продолжает независимые записи и не сообщает ложный rollback: он прекращает запись, дает диагностическую ошибку и требует восстановления по определенному протоколу.

Успешно полученный клиентом COMMIT обязан сохраняться в пределах проверенной модели отказов. Если соединение оборвалось до ответа, транзакция могла сохраниться. Приложению нужны уникальные идентификаторы операции/идемпотентность, чтобы безопасно повторять такие запросы.

Надежность зависит от реальных гарантий ОС, файловой системы и накопителя. SIGKILL проверяет падение процесса; он не заменяет симуляцию потери несинхронизированных записей и испытания отключения питания. Поддерживаемые среды фиксируются по результатам испытаний.

## 6. Лимиты и ошибки

До alpha зафиксировать пределы: длина сетевого сообщения и SQL, строка, cache budget, write-set, сортировка, результат, число соединений и prepared statements, время запроса и транзакции. Они должны иметь воспроизводимые граничные тесты.

Предел кэша не равен общему пределу RSS процесса. Учет памяти включает соединения, планы, приватные страницы, сортировки и результаты. Конкурентный admission control не допускает превышения общего заявленного бюджета из-за суммы клиентов.

Повреждение базы не исправляется молча. Команда восстановления или ремонта работает с копией и сообщает, какие данные могут быть потеряны. Неизвестный формат явно отклоняется.

## 7. Совместимость и платформа

Первый производственный целевой профиль: Linux x86_64, локальный диск, одна документированная файловая система. macOS ARM64 используется для разработки; отдельный производственный статус потребует подтверждения синхронизации и crash behavior именно на macOS.

Первый сетевой контракт — ограниченное подмножество PostgreSQL protocol с подтвержденными psql и одним драйвером. Необходимые типы, параметры, бинарные форматы и каталоговые запросы перечисляются в матрице. Полная работа pgAdmin потребует значительно большего системного каталога.

## 8. Решения, которые нужно принять до реализации

- [ ] Первая нагрузка, метрика лидерства и ограничения пользователя.
- [ ] Размер страницы, предельная строка, стратегия больших значений.
- [ ] Физическое размещение каталога, деревьев и WAL.
- [ ] Формат WAL и crash-safe checkpoint metadata.
- [ ] Точное поведение ошибок commit и отмены в разных состояниях.
- [ ] Таймауты, политика очереди блокировок и лимиты памяти.
- [ ] Способ backup и допустимое окно остановки записи.
- [ ] Первый драйвер, версия протокола и необходимые кодировки типов.
- [ ] Поддерживаемая файловая система и модель потери питания.
- [ ] Политика версий формата, обновления и обратного переноса данных.

Эта архитектура минимизирует начальную сложность. Условие продолжения — подтвержденная пригодность для продукта и измерения. Если цель лидерства противоречит выбранной модели, меняем модель и планируем соответствующую работу.
