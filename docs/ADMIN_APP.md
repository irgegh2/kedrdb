# Приложение управления KedrDB

Дата: 10 октября 2026 года. Статус: этап 6 принят на macOS/Linux, доказательства в [отчете](milestones/06.md); дальнейшее развитие — этапы 7–10. Название подтверждено пользователем — **Kedr Studio**, отдельный desktop binary на Rust. GUI — закрепленные eframe/egui 0.35.0, сеть — tokio-postgres 0.7.18 с TLS. Приложение входит в состав рыночной 1.0; количество этапов остается 11 (0–10).

Новое поручение пользователя: **в этапе 6 сначала реализуем админку**, затем необходимую серверную поддержку и интеграцию. Совместные номера выпусков и независимое обновление компонентов описаны в [VERSIONS.md](VERSIONS.md). Базовая совместимость разных версий закладывается с 1.0; широкая матрица будущих сочетаний проверяется по мере выпуска.

## Архитектура

Уточнение пользователя: версия 1.0 — **минимальный MVP с простым аккуратным интерфейсом**. Расширенные формы, мастера и dashboards не блокируют выпуск. Минимум: подключение, список таблиц/столбцов, SQL editor, результаты/ошибки, отмена, статус и `.sql` файлы. Слева объекты, справа editor, снизу результаты; более выразительный дизайн развивается позже.

Нативное приложение для macOS (компьютер пользователя) и Linux (первая серверная платформа). GUI и прикладная логика пишутся на Rust. Возможность Windows будет оценена отдельно; выпуск 1.0 не требует непроверенной поддержки Windows. Нет обязательного платного облака или платного API.

Приложение подключается к запущенному серверу KedrDB через проверенный клиентский протокол. Оно не редактирует data/WAL файлы напрямую и не является местом реализации транзакций, SQL или резервных копий. СУБД остается работоспособной через psql/драйвер без GUI. Backup/restore и перенос в 1.0 доступны через проверенные инструменты СУБД/CLI; графические мастера откладываются.

Порядок реализации: окно/editor/results и состояния на отделенном клиентском адаптере → согласование необходимого каталога и контрактов → сервер → подключение к настоящей базе. Временный тестовый адаптер явно обозначается, его данные не являются пользовательскими; он не засчитывается в приемку этапа. Этот порядок не меняет направление подключения и ответственность за транзакции.

UI thread не выполняет сеть или долгий SQL. Фоновые задачи имеют ограниченные очереди и отмену. Результаты ограничены, большие таблицы показываются с лимитом и навигацией; приложение не загружает всю таблицу в память. Пароли не записываются в обычные конфиги или логи, в MVP запрашиваются при подключении. Системное хранилище секретов может быть добавлено после 1.0.

Цель — быстрый, понятный и аккуратный инструмент для ежедневной работы. Утверждения «быстрее/лучше pgAdmin» появятся только после сравнения на одинаковых задачах. Полная поддержка PostgreSQL серверов нашим приложением не входит в 1.0.

## Этап 6: подключиться и выполнить SQL

- [x] Отдельный crate/binary, простое главное окно, читаемая типографика, понятные состояния загрузки/ошибки; одна аккуратная тема достаточна.
- [x] Подключение: адрес, порт, база, пользователь, TLS с проверкой сертификата; ввод пароля без сохранения в конфиге.
- [x] Плоский список таблиц и отдельная структура из реального каталога KedrDB: таблицы, столбцы, типы, ограничения, индексы.
- [x] SQL editor: выполнение выбранного текста, ошибки с понятным местом/кодом, остановка запроса, явное отображение состояния транзакции.
- [x] Ограниченная таблица результатов с корректными NULL/типами, прокруткой, копированием значения и указанием усечения.
- [x] Создание таблицы и запись первых строк через SQL; визуальные конструкторы не требуются к 1.0.

Приемка: на macOS и Linux подключение к настоящему серверу, SELECT/параметризованный CRUD/BEGIN/COMMIT/ROLLBACK, ошибка, отмена и потеря связи. Долгий запрос не замораживает интерфейс; повторное подключение не повторяет неопределенный COMMIT автоматически.

## Этап 7: ежедневная работа

С этапа 7 действует новый порядок пользователя: сначала возможности СУБД/CLI, затем их использование в Studio. Приоритет Studio из этапа 6 больше не задает последовательность следующих этапов.

- [ ] Открытие/сохранение ограниченного `.sql` файла и копирование значения из результата.
- [ ] Обновление списка объектов после DDL, отображение структуры таблицы и корректных NULL/типов.
- [ ] Понятный статус соединения/транзакции, сообщения server errors и неопределенного commit; reconnect без автоматического повтора записи.
- [ ] Инструкция по использованию CLI backup/restore/export/import рядом с quickstart приложения; отдельные GUI-мастера не требуются.

Приемка: полный учебный сценарий через SQL editor, файлы SQL, корректное обновление объектов и обработка потери связи. Приемка backup/restore со сверкой данных остается обязательной для СУБД/CLI.

- [ ] Измерять задержку самого UI отдельно от выполнения SQL и сети; сохранять сценарии, версии, размеры результатов и сырые данные.
- [ ] Ограничить большие списки/результаты и кэш, устранить повторные запросы каталога и лишние перерисовки; виртуализация по фактической необходимости.
- [ ] Сохранить измерения базового GUI-сценария. Сравнение с pgAdmin полезно, но победа GUI не является обязательной целью MVP.

Приемка: утвержденные до измерений бюджеты запуска/памяти/отклика пройдены; обработка больших результатов остается ограниченной по памяти; оптимизация не нарушает отображение NULL/типов или отмену. Быстрый GUI не засчитывается как ускорение СУБД в benchmark ядра.

## Этап 9: реальные пользователи

- [ ] Пилоты работают с базой через приложение и через драйвер; собраны конкретные проблемы ежедневных сценариев.
- [ ] Проверены установка без toolchain, первый запуск, навигация с клавиатуры и читаемость при масштабировании; дополнительные темы не блокируют MVP.
- [ ] Долгие сессии, повторные подключения, смена сети, истечение учетных данных, ошибки запросов и аварийное завершение GUI не повреждают данные.

Приемка: два независимых пилота выполняют свои задачи, не обходя приложение из-за блокирующих дефектов. Проверки GUI дополняют и не сокращают 72-часовой soak, 30-дневные пилоты и рассмотрение надежности ядра.
