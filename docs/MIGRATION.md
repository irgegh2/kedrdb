# KedrDB: проверяемый перенос из других СУБД

Дата: 10 октября 2026 года. Статус: **первый offline PostgreSQL adapter реализован на этапе 7, локальная приемка PG 18.2 пройдена; PG 16 и перенос между OS проверяются в CI**. Клиентские базы и внешние серверы не менялись: harness создает отдельный синтетический PostgreSQL cluster. Ядро/сервер/Studio на Rust; миграционный инструмент Python использует psycopg 3, не входит в ядро.

## Рабочие команды первого адаптера

Подключение задается libpq environment либо `PGSERVICE`/`PGSERVICEFILE` и приватным `PGPASSFILE`, не паролем/DSN в аргументах. Допускается Unix socket или TCP с `sslmode=verify-full`. В журналах инструмента только коды ошибок/количества, не строки/SQL/credentials. Нужны права SELECT и достаточные права на SHARE lock; инструмент их не расширяет.

```sh
python3 tools/migrate_postgres.py preflight
# Предварительно остановить ВСЕ приложения, фоновые писатели и DDL:
python3 tools/migrate_postgres.py snapshot --job migration-001 --writes-stopped
python3 tools/migrate_postgres.py import --job migration-001 --kedr target/release/kedr
# Той же командой import продолжить после обрыва из сохраненного snapshot.
```

`--writes-stopped` — подтверждение оператора, не магическое отключение чужих клиентов. Инструмент берет SHARE locks всех существующих таблиц **до первого SELECT snapshot**, выполняет единый REPEATABLE READ и rechecks схему. Эти locks блокируют INSERT/UPDATE/DELETE/DDL существующих таблиц; они не запрещают создание новых объектов другим администратором. Поэтому внешний запрет писателей/DDL обязателен. [PostgreSQL LOCK](https://www.postgresql.org/docs/18/sql-lock.html) описывает связь порядка lock и первого snapshot. Preflight не меняет источник; snapshot не выполняет DML/DDL, но создает locks и удерживает их во время копирования.

Поддерживаемый профиль v1: PostgreSQL 16–18, только `public`, до 128 обычных persistent tables/256 columns, INT/BIGINT/TEXT/BOOLEAN, один **явный BIGINT PRIMARY KEY** без identity/default, одно поле UNIQUE/FK к BIGINT PK, обычный одно-полевой B-tree индекс. TEXT только с bytewise C/POSIX collation (либо database default C/POSIX libc). Размеры encoded rows/index keys/SQL проверяются при streaming snapshot; preflight catalog не заявляет, что все строки уже проверены.

NUMERIC/date/timestamp/JSON/UUID, sequences/defaults/identity/generated, CHECK, composite PK/FK/index, deferred/cascading FK, RLS/custom ACL, user triggers/rules/routines, views/partitions/inheritance/foreign tables, extensions кроме plpgsql, domains/enums/ranges, expression/partial/INCLUDE/descending/custom-opclass/NULLS NOT DISTINCT indexes отклоняются. Межтабличный FK цикл не экспортируется; self-FK цикл допускается. Неподдерживаемое не преобразуется молча. Имена PK/UNIQUE/FK constraints нормализуются, внутренние IDs/индексы не сохраняются; роли/гранты/комментарии/replication settings/statistics не переносятся. Один администратор target — ограничение 1.0, готовность приложения проверяется отдельно.

Job 0700, snapshot/manifest 0600. Завершенный snapshot.sql и manifest.json пишутся после fsync, до их появления возобновление невозможно: нужен новый job/новое окно. После потери source соединения importer использует **только** уже завершенный snapshot, не подменяет его новым состоянием. Прогресс хранится в WAL target атомарно со строками. `.migration-incomplete` блокирует обычный сервер даже после SQL import; `complete-migration` напрямую сравнивает все байты canonical schema и типизированных значений, проверяет integrity/checkpoint и только затем снимает guard. Равный count/hash сам по себе не завершает перенос.

После успеха target находится в `migration-001/database`, verified.json фиксирует количества/сверку; `application_verified=false`. Выбор/переключение конфигурации приложения выполняется отдельно после прикладных проверок и проверки backup target. Источник не удаляется. Возврат после новых target writes не автоматизирован.

Воспроизводимая проверка на новом cluster: `python3 tools/check_stage7_maintenance.py --pg-bin /путь/к/PostgreSQL/bin --output новый-каталог`. Команды backup/restore/обычного SQL import — [OPERATIONS.md](OPERATIONS.md).

## Цель и границы

Перенос должен дать проверяемый отчет: что совместимо, что требует изменений приложения, что скопировано, что сверено и когда возможен возврат. Удобство миграции снижает барьер внедрения; само по себе оно не доказывает преимущество ядра.

Первый адаптер — PostgreSQL, только для явно поддерживаемого профиля схемы и версий источника. Затем отдельные адаптеры MySQL, MariaDB и SQLite по спросу пилотов. Их типы, журналы и SQL различаются; «поддержка MySQL» не автоматически доказывает поддержку MariaDB. Перенос из Oracle/SQL Server и любых других систем пока не включен в обязательства.

Первый рабочий режим — согласованное окно обслуживания с остановкой записи. Перенос с продолжающейся работой источника добавляется после отдельного протокола snapshot + change stream. Универсальную совместимость и отсутствие простоя не обещаем.

## 1. Проверка до копирования

- Считать каталог схемы и оценку объема, не меняя источник. Составить версионированный manifest: источник, таблицы, колонки, ключи, преобразования, настройки сравнения и версия target codec.
- Проверить типы и диапазоны, NULL, кодировки, сортировки, регистр идентификаторов, default/identity/sequence, PK/FK/unique/check, индексы, views, функции, triggers, расширения и права. Проверить используемые запросы и драйверы приложения отдельно от данных.
- Первоначальный SQL-профиль KedrDB ограничен INT/BIGINT, TEXT, BOOLEAN и явным BIGINT PK. Ограничение кодированной строки 8 КиБ тоже учитывается. Decimal/деньги, timestamps/time zones, JSON, UUID, большие значения и unsigned integers не преобразуются молча. Неподдерживаемое останавливает план или требует явного точного mapping и изменения приложения.
- Для полного сравнения нужна стабильная уникальная идентификация строк. Таблица без подходящего ключа в первом профиле отклоняется; автоматическое добавление ID не считается сохранением совместимости.
- Показать пользователю несовместимости и ожидаемое окно обслуживания до запуска. Отчет «таблицы скопированы» не равен «приложение готово работать».

Подключения используют минимальные необходимые права и защищенный канал/локальный сокет. Секреты не попадают в manifest, журнал, командную строку или отчет. Доступ чтения не дает права включать replication или менять конфигурацию чужого сервера; эти действия требуют отдельного подготовленного плана.

## 2. Первая версия: перенос с остановкой записи

1. Проверить восстановление резервной копии источника на отдельной копии. Подготовить пустую изолированную целевую базу и протестировать схему/запросы на пробном наборе.
2. Закрыть доступ к записи всем приложениям, фоновым задачам и административным клиентам; завершить ранее начатые транзакции. Проверить, что запрет действительно действует. Одна read-only транзакция импортера не останавливает других писателей.
3. Зафиксировать согласованный snapshot источника и схему. Копировать типизированные строки чанками с ограниченными памятью и нагрузкой; читать все связанные таблицы из одного согласованного состояния. Не выполнять произвольный чужой SQL dump внутри KedrDB.
4. Сохранять durable manifest и прогресс. Чанк и отметка о его применении фиксируются атомарно в целевой базе; повтор после сбоя не дублирует строки. Продолжение допускается только для того же snapshot/schema/mapping. Потеря PostgreSQL snapshot-сессии не разрешает незаметно продолжить со свежим snapshot: начать новую согласованную копию или использовать заранее сохраненный проверенный export.
5. Построить/проверить индексы и ограничения, выполнить полную сверку ниже. На целевой базе запись приложений пока закрыта. Любая несовместимость или несовпадение блокирует переключение.
6. Проверить восстановление резервной копии target. Выполнить прикладные проверки и переключить конфигурацию приложения. Открыть запись только на одной стороне; исключить работу части клиентов со старым источником.

Импортер не удаляет исходную базу. Частично загруженные данные не становятся рабочей базой. Пробный запуск и реальный перенос имеют отдельные каталоги/идентификаторы; существующий каталог target не перезаписывается.

## 3. Проверка результата

- Проверить схему, ключи, ограничения, число строк и отсутствие потерянных/дублированных ключей.
- Сравнить все поддерживаемые значения по ключам в стабильном порядке. Канонизация различает NULL/пустую строку, тип, длину и точные байты/числа; согласованное преобразование применяется одинаково с обеих сторон. Не сравнивать только вывод SELECT, зависящий от locale.
- Использовать криптографические hashes чанков для быстрой локализации различий, затем сравнивать строки/поля. Hash не является абсолютным математическим доказательством отсутствия различий. Режим полной проверки непосредственно сравнивает все канонические значения; выборочная проверка обозначается как выборочная.
- Проверить результаты реально используемых запросов, включая ORDER BY, NULL и границы чисел; defaults, генерацию ключей и права доступа, если они входят в поддерживаемый профиль.
- Сохранить отчет с версиями адаптеров, manifest, числом проверенных строк/полей, ошибками и состоянием переключения. Непроверенные объекты нельзя показывать зеленым «успехом».

Это известная инженерная практика: [AWS DMS validation](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Validating.html) сравнивает исходные и целевые записи и отмечает расхождения; проверка также нагружает обе базы. Наш инструмент должен ясно показывать свои границы и стоимость.

## 4. Возврат и переключение

До первых новых записей в KedrDB возврат возможен переключением приложения на сохраненный источник после проверки состояния. После новых записей старый источник уже не содержит новых заказов. Простое обратное переключение потеряет эти изменения.

Для возврата после открытия записи требуется отдельно проверенный путь: остановить запись, выгрузить новые изменения в точном порядке с учетом deletes/schema и применить их к источнику, затем полностью сверить результат; либо иметь заранее отрепетированную обратную репликацию. Такая возможность не обещается до реализации. Наличие старой базы или backup само по себе ее не обеспечивает.

Первый пилот заранее выбирает границу проверки до открытия записи и процедуру инцидента после нее. Система сохраняет миграционный отчет и операции target; откат не выполняется автоматически при неоднозначном результате. Одновременная независимая запись в две базы не является планом отката.

## 5. Позже: перенос с коротким окном переключения

Для PostgreSQL потребуются согласованный snapshot и связанная с ним позиция logical replication без пропуска промежуточных изменений. Slot/позиция создаются в правильном порядке; «сначала SELECT всех строк, потом включить журнал» может потерять изменения. Дальше:

- Начальная копия и поток изменений связываются одним протоколом; transaction boundaries, inserts/updates/deletes и изменения ключей сохраняются.
- Позиция подтверждается источнику только после durable применения целевой транзакции. Повтор после disconnect/restart не дублирует эффект. Точные crash-сценарии и ambiguous commit проверяются тестами.
- Ограничены буферы и отставание; показаны нагрузка и рост удерживаемого WAL. При потере требуемой истории перенос останавливается и повторяет snapshot, а не скрывает пропуск.
- DDL, последовательности и неподдерживаемые объекты проверяются отдельно; [PostgreSQL logical replication](https://www.postgresql.org/docs/18/logical-replication-restrictions.html) не переносит изменения схемы и состояние sequences автоматически.
- При финальном переключении запись источника останавливается, поток доходит до зафиксированной последней позиции, выполняется сверка на этой границе, затем приложение подключается к target. Обратный путь отдельно проверяется до открытия записи.

MySQL/MariaDB потребуют собственного протокола binlog/GTID и типов; SQLite — своего snapshot/окна записи. Эти адаптеры не добавляются просто заменой строки подключения PostgreSQL.

## Пользовательский интерфейс

Будущий мастер: **подключить → увидеть совместимость → выполнить пробу → перенести → увидеть отчет сверки → переключить**. На каждом шаге показывать текущее состояние, возобновляемость и доступный путь возврата. До переключения оператор видит конкретный результат; автоматизация копирования не означает автоматическое переключение неподготовленного приложения.

## Критерии включения в выпуск

- Этапы 5–6: реальные schema/SQL и клиентский API; определить точный поддерживаемый миграционный профиль.
- Этап 7: offline-импортер, backup/restore, manifest, повтор после сбоя, полная сверка и отрицательные тесты несовместимых схем.
- Этап 9: перенос независимого пилотного приложения на копии, отрепетированное переключение/возврат; тесты прерывания копирования и запрет split-brain записи.
- Этап 10: публиковать только фактически проверенные направления, версии и ограничения. Online CDC не обязательный пункт первого выпуска без отдельного решения.

Чек-лист тестов: NULL/Unicode/пустые строки/числовые границы; слишком большие строки; конфликт keys/FK; падение между data и progress; потеря snapshot; несовпадение schema после preflight; mismatch одной строки при равном count; старый клиент продолжает писать; возврат после target-записей. Имитировать на синтетических данных, затем подтверждать на согласованных копиях пилотов.
